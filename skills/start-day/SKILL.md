# start-day

その日の自走を始める「起動スキル」。board（または人間）が各エージェントワークスペースで `claude "/claude-flywheel:start-day"` を実行するだけで、cadence 設定の読み込み → 初回 `run-cycle` → セッション内 cron 登録までを行う。

> **セッション内 cron 方式を採用**: Claude Code のセッション内 cron（CronCreate 等）は **REPL アイドル時のみ発火**するため、`run-cycle` 実行中に次の定期便が来ても終了まで待つ＝セッション内で自然に直列化される（`.flywheel/cycle.lock` は手動併走への保険として引き続き機能）。本スキルが登録するジョブは**すべて起動日の日付に固定した one-shot**（recurring なし）であり、発火後は自動削除される（recurring の 7 日自動失効は関係しない）。**対話割り込み中は発火が遅延**する（承認対話を邪魔しない望ましい挙動）。セッション（board の埋め込みターミナル等）を閉じれば自走は一旦停止するが、**永続的なキルスイッチではない**（`--resume`/`--continue` でセッションを再開すると、未発火の one-shot cron が復元され得るため。ただし各ジョブは日付固定かつプロンプト内に日付ガードを持つため、起動日を過ぎての発火・実行は構造的に防がれる）。永続的に止めたい場合は、CronList で `flywheel-` プレフィックスのジョブを検出し CronDelete で削除する（手順3・手順5と同じ名前パターンで一括検出できる）。詳細な採用理由・不採用選択肢（launchd／クラウド routine）は upstream の要件チケットおよび `docs/architecture.md` §7 を参照。

## 前提

- ブートストラップ済み（`positions/`・`memory/`・`challenge-ledger.md` が存在。無ければ `flywheel-init` / `bootstrap-domain-map` を先に実行）。
- Claude Code のセッション内 cron ツール（CronCreate 等）が使えるランタイムで、対話セッションとして起動していること（cron はセッションに紐づく）。

## 入力（任意）

- なし。cadence 設定はワークスペースの `.flywheel/cadence.json` から読む。

## 手順

### 1. cadence 設定の読み込み

- `.flywheel/cadence.json` を Read する（雛形は `${CLAUDE_PLUGIN_ROOT}/templates/cadence.json`。`flywheel-init` が scaffold 済みのはず）。
- **存在しない、または JSON としてパース不可**の場合は既定値で続行し、報告に「cadence 設定が無い（または壊れている）ため既定値で動作している」旨を明記する。既定値:
  - 業務曜日: 月〜金（`business_days: "1-5"`。`0`/`7`＝日曜、`6`＝土曜という一般的な crontab 表記に従う。**本スキルは cron 式にもガード判定にも使用しない**＝「当日働くかどうか」は本スキルを起動するか否かで表現する。`business_days` は board 等の上位レイヤーが「その日 start-day を起動するか」を判定するための宣言値として cadence.json に保持する〔後方互換のためフィールドは残す〕）
  - 業務時間: `10:00`–`18:00`
  - run-cycle 間隔: 90 分
  - 発火分オフセット: **未指定（`null` を含む）が既定**。その場合は**ワークスペース名（ディレクトリ名）から決定的に導出**した値を使う（例: 名前の文字コード和を 59 で割った剰余 + 1。結果が `0`/`30` なら 1 ずらす）。導出した値は `.flywheel/cadence.json` の `cron_minute_offset` に**書き戻して固定**する（fleet 内の他エージェントと発火分が重なりにくく、かつ翌日以降も同じ値で安定させるため。テンプレートが全ワークスペースに同一の固定値を配ると、ずらす目的自体が無効になるので既定値は持たない）
  - reflect しきい値: 10 周ごと（`reflect.every_n_cycles`。同種 bad の再発しきい値は reflect スキル既定の `recurrence ≥ 2` をそのまま使い、cadence.json には持たせない＝二重定義を避ける）
  - 定期監査ジョブ: **既定なし＝未宣言（`audit` ブロック不在、または `audit.jobs` が空なら定期監査を行わない）**。他フィールドと違い既定値で補完しない**opt-in 設定**であり、雛形（`${CLAUDE_PLUGIN_ROOT}/templates/cadence.json`）にも含めない。監査を回したいワークスペースだけが `{"audit": {"jobs": [{"id": "...", "title": "...", "skill": "...", "skill_label": "...", "every_n_cycles": 30}]}}` を明示的に足す（監査は対象 repo ごとの LLM fan-out でコストが大きく、宣言していないワークスペースで勝手に発生させないため）。**`skill` が指す監査の意味を flywheel は解釈しない**（ジョブ宣言は接続ツールへの委譲内容そのもの）。ブロックがある場合の判定・起動は run-cycle 手順0 が行う（本スキルは値の検証のみ）
  - 実行モード: `native`（`execution_mode`。ホスト直実行。コンテナ隔離モード `container` を使う場合の意味は本手順末尾を参照）
- ファイルは存在するが一部フィールドのみ欠けている場合は、その項目だけ既定値で補い、欠落したフィールド名を報告に含める（全欠落と部分欠落を区別して報告する）。
- **値の妥当性検証**: 存在するフィールドについても値そのものを検証する。妥当条件は次の通り:
  - `run_cycle_interval_minutes` / `reflect.every_n_cycles`: 正の整数
  - `audit.jobs[]`（`audit` ブロックがある場合のみ検証。**不在は不正値ではなく「未宣言＝OFF」**なので欠落フィールドとして報告しない）: **検証規則の正本は periodic-audit の §ジョブ宣言の検証**（`${CLAUDE_PLUGIN_ROOT}/skills/periodic-audit/SKILL.md`）であり、本スキルは同じ規則を適用する — `id` は **`^[A-Za-z0-9._-]{1,64}$` に一致**しジョブ間で一意、`title` は 1〜200 文字、`skill` は 1〜500 文字（いずれも制御文字・改行を含まない）、`skill_label` は省略可で **`^[A-Za-z0-9._/-]{1,64}$`**、`every_n_cycles` は正の整数、`adapter` は省略可の文字列。**`id` は台帳の監査元マーカー `<!-- audit:<id>:<repo名> ... -->` に焼き付く永続識別子**であり、改行・制御文字・`-->` 等が入るとマーカーの境界が壊れて冪等判定が失敗するため、**エスケープではなく許可文字リストで弾く**。**本ブロックは他フィールドと違い不正値を既定値へ補正せず**（`every_n_cycles` も含む）、違反したジョブを**無効化して `id` と理由を報告**する（台帳という永続データへの書き込みを駆動する設定のため安全側に倒す）。`audit` が非オブジェクト・`jobs` が非配列の場合は**ブロック全体を無効**にする。**本スキルの検証は必須の前提にならない**（`/run-cycle` の直接実行・既存 cron・start-day 後の cadence 編集は本スキルを経由しない）ため、**run-cycle 手順0 と periodic-audit も委譲前に同じ検証を自分で実行する**
  - `business_start` / `business_end`: `HH:MM` 形式（`HH` は `00`–`23`、`MM` は `00`–`59` の数値範囲）かつ `business_start < business_end`
  - `cron_minute_offset`: `null`、または 0–59 の整数
  - `business_days`: 有効な cron 曜日式（`1-5` や `0,6` など。範囲外の値・構文不正を含まない。本スキルは値を使用しないが、上位レイヤー向けの宣言値として形式検証は維持する）
  - `execution_mode`: `native` または `container` のいずれか
  - **不正な値は欠落フィールドと同じ扱い**とする（部分欠落の扱いと一貫させる）。該当項目だけ既定値へ補正し、補正したフィールド名を欠落フィールドと合わせて報告に含める。他の妥当なフィールドはそのまま使う。**中止はしない**（拍動の起点である本スキルが設定ミス1つで止まらないようにするため）。**例外: `execution_mode` の不正値はこの「補正して継続」の対象外**とする（後述の「`execution_mode` の妥当性検証は fail-closed」を参照）。
- **`execution_mode: container` の意味**: このセッション自体が**コンテナ内で実行されていること**を前提とする設定であり、コンテナの起動自体（`docker compose up -d`）は本スキルの**外側**（人間）が行う。本スキルはコンテナの起動・停止を行わない（雛形は `${CLAUDE_PLUGIN_ROOT}/templates/container/`。scaffold 後の利用先ワークスペースでの前提条件・既知の制約は `runtime/README.md`「container モードの前提条件」を参照）。
- **`execution_mode` の妥当性検証は fail-closed（他フィールドの「安全側に補正して継続」規律の例外）**: `execution_mode` の**キー自体が存在しない場合のみ**、従来通り既定値 `native` を補って継続する（後方互換）。一方、キーが存在して値が `null`、または `native`/`container` のいずれでもない場合は**明示的な不正値**として扱い、既定値へ補正せず、初回 `run-cycle` の実行（手順2）および定期便の cron 登録（手順3）より**前で処理を停止**し、不正な値の内容を理由とともに報告する（`cron_minute_offset` の `null` は「未指定」を示す正当な値だが、`execution_mode` の `null` はキーが明示的に存在する不正値であり意味が異なる）。理由: `run_cycle_interval_minutes` 等の他フィールドは、設定ミス1つで拍動の起点である本スキルが止まらないよう可用性を優先して安全側に補正するが、`execution_mode` は**隔離境界を宣言する設定**であり、設定 typo や誤起動をそのまま既定値で補正して自走してしまうと「隔離されているつもり」でホスト上に実行が漏れるリスクの方が、拍動が1周止まるリスクより大きい。そのため本フィールドの不正値に限り、可用性より安全側＝停止を優先する例外とする。
- **宣言と実態の食い違いの検知（`execution_mode: container` の場合のみ・fail-closed）**: `/.dockerenv` の存在、または `/proc/1/cgroup` に `docker`/コンテナランタイム由来の記述が含まれるかを確認する。いずれの兆候も確認できない場合は、「`execution_mode: container` と宣言されているが、コンテナ内で実行されている形跡が確認できない」旨を理由として明記したうえで、初回 `run-cycle` の実行（手順2）および定期便の cron 登録（手順3）より**前で処理を停止**する。人間が実態を確認し、`execution_mode` の設定を修正するか、コンテナを正しく起動したうえで本スキルを再実行することを促す。隔離境界に関わるフィールドであるため、上記と同じ理由（Issue #54 のコンテナ隔離目的）で fail-closed とする。

### 2. 初回 run-cycle の即時実行

- `run-cycle` スキル（`${CLAUDE_PLUGIN_ROOT}/skills/run-cycle/SKILL.md`。Skill ツールがあれば `claude-flywheel:run-cycle` として呼び出してよい）を通常モード（`--dry-run` なし）で 1 周実行する。
- cron 登録前に必ず 1 回実行する（設定ミス・権限不備の早期検知、および「起動したら動き出す」体感のため）。
- 実行結果（サイクルレポート）はこのスキルの最終出力にそのまま含める。

### 3. run-cycle 定期便（起動日の日付固定 one-shot cron 群）の登録

> 本手順は「**準備（算出・変換・検証・上限判定）→ 掃除 → 登録**」の順で行う。既存ジョブの削除は準備がすべて成功した後にのみ実施する（準備段階で失敗した場合に、正常に動作していた旧スケジュールだけが消えて自走が止まる事態を防ぐため）。

- 手順1の cadence（業務開始・終了・run-cycle 間隔・発火分オフセット）から、当日の発火時刻の一覧を算出する（業務終了時刻**以降**の発火、および**現在時刻（登録時点）以前の発火は含めない**。過去時刻の日付固定 one-shot は当日中に発火し得ず登録が無駄になるうえ、環境によっては即時発火扱いとなり run-cycle が重複起動しかねないため。起動時点の 1 周は手順2の初回 run-cycle が既に担っており、過去分の追い掛け発火は不要）。以降のジョブ数見積もり・登録は、すべてこの**除外後の一覧**を使う。
  - 例: 開始 `10:00`・間隔 90 分・オフセット 5 分・`09:00` 起動 → `10:05, 11:35, 13:05, 14:35, 16:05, 17:35` の 6 件。同設定で `14:00` 起動なら過去分を除いた `14:35, 16:05, 17:35` の 3 件のみ。
  - 一覧が**空**になる場合（最終発火時刻より後の起動）は、定期便の登録は行わず（後述の既存ジョブ掃除は行う）手順5へ進む（手順5の遅延起動時フォールバックが即時の締め処理を担う）。
- 算出した各発火時刻を、**1 発火時刻＝1 の one-shot cron ジョブ**（**recurring なし**）として、**起動日のローカル日付を日・月フィールドに固定した** 5 フィールド cron 式（`分 時 <日> <月> *`・ローカルタイム。**曜日フィールドは使わず `*` 固定**）へ変換する（例: 8/14 起動で上記なら `5 10 14 8 *`, `35 11 14 8 *`, `5 13 14 8 *`, `35 14 14 8 *`, `5 16 14 8 *`, `35 17 14 8 *` の 6 ジョブ）。日付固定の one-shot は発火後に自動削除され、かつ cron 式が起動日以外の日付にマッチしないため、**締めジョブが発火しなくても・セッションが `--resume` で再開されても翌日以降に発火しない**（「当日限定」の保証を、締めジョブの発火というランタイム条件ではなく cron 式の静的性質で持つ＝自己清掃・fail-safe）。登録は後述の掃除の後に行う。
  - **変換の自己検証（必須）**: 変換した cron 式群を発火時刻の一覧へ**逆展開**（1 ジョブ＝1 発火時刻）し、冒頭で算出した一覧と完全一致すること、および**全ジョブの日・月フィールドが起動日のローカル日付と一致すること**を確認する（変換は決定的な機械処理であり、誤ると静かに誤時刻・誤日付で発火するため。scripts/ への抽出は [#46](https://github.com/masanami/claude-flywheel/issues/46) の抽出基準〔散文でのレビュー往復・複数箇所での重複・静かに壊れる〕に照らして運用の実痛が出てから判断する）。
- **ジョブ数の見積もり（既存ジョブ削除前・必須）**: セッション内 cron には**セッション全体**での登録数の上限（目安 50 件前後）があるため、既存ジョブの掃除に着手する前に、CronList で**削除対象外（手順3・手順5の `flywheel-` プレフィックス以外）の残存ジョブ数**を数え、登録予定のジョブ数（**冒頭で算出した〔過去分除外後の〕発火時刻の総数**。1 発火時刻＝1 ジョブのため）に、**手順5で締めジョブを登録する経路の場合のみ one-shot 締めジョブ 1 件**を加えて見積もる（通常経路では手順5が one-shot 締めジョブを追加登録するため、これを含めずに判定すると締めジョブ登録時に上限を超えて失敗し得る。逆に、手順5が締めジョブを登録しない経路〔発火時刻が過去で即時締め処理になる遅延起動〕では `+1` を加算しない＝過大見積もりで有効な登録を誤って中止しないため）。**残存ジョブ数 + 定期便の新規予定数 + 締めジョブ分（登録する場合のみ 1、しない場合は 0）≤ 50** を満たさない場合は、既存ジョブを削除せずに安全に中止し、cadence 設定（間隔が短すぎる等）の見直しを促す報告をして終了する（一部だけ登録されて静かに欠落する事態を避けるため）。
- **既存の flywheel cron ジョブの掃除（再実行の冪等化・必須。上記の準備がすべて成功した後にのみ実施）**: CronList 等で本手順・手順5の名前プレフィックスに一致する既存ジョブを検出し、残っていれば**全削除する**（発火済みの one-shot は自動削除されるため通常は残らないが、同一ワークスペースでの本スキル再実行時の当日未発火分・前日以前の残骸が残り得る。二重登録を防ぐ。「何度起動しても二重実行しない」冪等原則を拍動レイヤーにも適用する。見つからなければ何もしない）。削除の前に**削除対象ジョブの構成（ジョブ名・cron 式・プロンプト・`recurring` の実値など、同一構成での再登録に必要な属性一式）を控えておく**。**削除が途中で失敗した場合は、新規登録へ進まない**。控えから**削除済みのジョブを控えた属性のとおり再登録して旧構成へ復元**し、CronList で復元結果を確認したうえで、失敗内容を報告して本手順を中止する（削除済み分を復元しないと旧スケジュールが欠落したまま自走が細るため。復元にも失敗したジョブは「未復旧」として名前・cron 式を明示して報告する。旧ジョブが本方式〔日付固定 one-shot〕なら残っても翌日以降は発火・実行しないが、旧方式〔recurring〕の残骸にはその保証が無いため、残存を無害とは扱わない）。直後の登録が途中で失敗した場合は、**まず登録済みの新規ジョブをすべて削除してから**（このため新規ジョブの ID は登録のつど控える）、控えから旧構成を控えた属性のとおり再登録して旧スケジュールへ復旧する（旧の再登録だけでは部分登録済みの新規ジョブと併存して同時刻に二重発火するため、復旧は「新規の全削除 → 旧の再登録」の順で行う。削除→登録の間で失敗しても自走が止まったまま放置されないようにするため）。
- 掃除が終わったら、検証済みの cron 式を **1 発火時刻＝1 one-shot cron ジョブ**として CronCreate で登録する（**`recurring: false` を明示指定する**。CronCreate の `recurring` は省略時に recurring 登録として扱われ得るため、既定値に依存しない）。
- **分はエージェントごとにずらす**（fleet で複数エージェントを同時運用するため。`cadence.json` の発火分オフセットを使う。全員が `:00`/`:30` に発火すると API バーストとサブスク消費が重なるため避ける）。
- **ジョブ名は discoverable な共通プレフィックス**（例: `flywheel-run-cycle-<ワークスペース名>-<連番>`）を付けて登録する。発火時刻ごとに複数ジョブへ分かれるため、後続の手順（手順4の兄弟ジョブ削除・手順5の締めジョブ）が CronList 等で**名前パターンで一括検出**でき、個々の ID を手渡しで追跡し続けなくてよいようにするため（1 件目の登録時点では後続ジョブの ID がまだ確定していない、という手順4向けの相互参照問題を避ける）。
- 各ジョブのプロンプトには、`/claude-flywheel:run-cycle` の実行に加えて**手順4の課題枯渇時の自動停止判定**を含める。
- **実行時ガード（必須）**: cron 式の日付固定・逆展開検証は登録時点の静的な整合しか保証しないため、登録時に**起動日のローカル日付（`YYYY-MM-DD`）を各ジョブのプロンプトに対象日として埋め込み**、プロンプト冒頭に次の 2 判定を含める。いずれかを満たさない場合は `run-cycle` を実行せず、その旨を報告して終了する:
  1. **日付一致**: 実行時のローカル日付が埋め込んだ対象日と一致すること（REPL アイドル待ち・対話割り込みによる発火遅延で日付境界を跨いだ場合のスキップ。手順5の締めジョブの日付ガードと同じ規律を定期便側にも持たせる）。
  2. **時刻範囲**: 実行時のローカル時刻が cadence の業務時間（`business_start`–`business_end`）内であること（発火の遅延ジッターで業務時間外に run-cycle が走ることを防ぐため）。
  - **業務曜日（`business_days`）の判定は行わない**（「起動日＝営業日」の方針。本スキルを起動した日は曜日に関わらず働く日であり、曜日は cron 式にも実行時ガードにも使わない）。境界の裁量は持たせず、単純な日付・時刻比較で判定する。
- 登録した各ジョブの ID（および上記の名前プレフィックス）を控えておく（手順5の締めジョブ・手順4の兄弟ジョブ削除が対象を特定するため）。

### 4. 課題枯渇時の自動停止（各定期便のプロンプトに含める判定）

手順3で登録する run-cycle 定期便のプロンプトには、`run-cycle` が**正常終了**した後に次を行うよう明記する（`run-cycle` スキル自体は変更しない。判定はこの定期便プロンプト側の指示として持たせる）:

- **正常完了が前提（必須）**: `run-cycle` がエラー・失敗で終わった場合、または観測ステップ（ingest）・台帳（アーカイブ含む）の確認が正常に完了しなかった場合は、**枯渇判定を行わず（ジョブも削除せず）**、エラー内容を報告して終了する（次の定期便で再試行される）。「確認できなかった」を「新規取り込みなし・未完了なし」と扱わない（エラー時の誤判定で定期便を削除して自走を止めないため）。
- 台帳（`challenge-ledger.md`。アーカイブ `challenge-archive*.md` を含めて確認）を確認し、**未完了の課題が 1 件も無い**（全課題が完了・アーカイブ済み。かつ当周の観測ステップ〔ingest〕でも新規取り込みが無かった）場合:
  - この定期ジョブ（および同じく登録済みの他の run-cycle 定期便ジョブがあればそれも）を削除する。**他ジョブの削除は、手順3の名前プレフィックスで CronList 等から検出して行う**（このジョブが作成された時点で他ジョブの ID が確定していないケースがあるため、ID の事前埋め込みに依存しない）。
  - 「課題が枯渇した。次は要件定義（課題の起票）から」と報告して終了する。
  - 手順5の締めジョブは、対象が無くなるため合わせて削除してよい（同様に名前パターンで検出。削除できない場合は締めジョブ側の自己防御＝「定期便が既に無ければ何もしない」に委ねてよい）。
- **`計画承認待ち` / `完了確認待ち` の課題が残っている場合は止めない**（人間の承認が入れば次周から前進できるため）。この場合の周回は軽い観測のみで終わってよい。

### 5. 就業前の締めジョブ（one-shot cron）の登録

- **起動日＝営業日の方針（本手順の冒頭）**: 締めジョブは、**起動日の曜日に関わらず登録する**（本スキルを起動した日＝働く日。「当日働くかどうか」は `business_days` ではなく start-day を起動するか否かで表現する）。旧設計にあった非営業日ガード（業務曜日でない日は締めジョブを登録しない）は撤廃する。同ガードが防いでいた「翌営業日向けに残っている定期便を非営業日の夜に誤って削除する」事故は、手順3の定期便が起動日の日付固定 one-shot になったことで**構造的に消えている**（翌日以降に発火し得る定期便がそもそも残らないため、削除してはいけない定期便が存在しない）。
- 業務終了時刻の直前（例: 終業 15 分前。cadence に専用の項目が無ければこの固定値を使う）に発火する **one-shot** の cron を CronCreate で登録する（手順3と同じく **`recurring: false` を明示指定**する）。**算出した締め時刻が業務開始時刻より前になる場合**（業務時間が前倒し分より短い設定）は、業務時間内に収まるよう**終業直前（例: 終業 1 分前）へクランプ**し、補正した旨を報告に含める（手順1の値検証と同じ「安全側に補正して継続する」規律）。**ジョブ名は `flywheel-close-<ワークスペース名>-<日付>` とする**（手順3の run-cycle 定期便と同じ discoverable な `flywheel-` プレフィックス配下に、締めジョブと識別できる固有パターンを設ける。手順3冒頭の既存ジョブ掃除はこのパターンも検出対象に含め、旧 one-shot が残ったまま再登録されて締め処理が重複実行される事態を防ぐ）。
- **対象日の埋め込み（必須）**: 登録時に、**登録日のローカル日付（`YYYY-MM-DD`）をジョブのプロンプトに埋め込む**（ジョブ名の `<日付>` と同じ値。締め処理の対象がどの日であるかを、実行時のローカル日付に頼らずジョブ自身が保持するため）。
- **遅延起動時のフォールバック（必須）**: 上記で算出した締めジョブの発火時刻が**現在時刻を過ぎている**場合（start-day 自体が終業直前〜終業後に起動されたケース）、one-shot は発火しないため登録せず、**この場で即時に下記の締め処理（1〜3）を実行する**。この場合、当日の run-cycle 定期便はもう発火しないため、手順3で登録した定期便が残っていれば削除も行う（＝通常の締めと同じ動作を、cron 経由ではなくその場で行うだけ）。
- **日付ガード（必須）**: 締めジョブのプロンプト冒頭に、実行時のローカル日付を確認する判定を含める。**埋め込んだ対象日と一致しない場合は、締め処理（サマリ報告・定期便削除・reflect 判定のいずれも）を一切行わず**、対象日と実行日を明示して終了する。理由: セッション内 cron は REPL アイドル時のみ発火するため、`--resume` での再開後に日付境界を跨いで翌日発火するケースがあり得る。その場合に旧締めジョブがそのまま処理を実行すると、翌朝の `start-day` が登録し直した**当日の run-cycle 定期便を誤って削除**してしまう。対象日不一致時は何もしないのが安全側であり、旧ジョブは one-shot なので発火後に自然消滅する（別途の削除操作は不要）。
- プロンプトには（即時実行の場合はこのセッションでの実行手順として。日付ガードを満たした場合のみ）次を含める:
  1. 本日のサイクルサマリ（当日分の journal・台帳の状態）を報告する。
  2. 手順3で登録した run-cycle 定期便ジョブのうち**未発火で残っているもの**を削除する（発火済みの one-shot は自動削除されている。すでに手順4の自動停止で削除済みなら何もしない。定期便が日付固定 one-shot になったため、この削除は「当日限定」を保証する必須処理ではなく**自己清掃のバックアップ**であり、締めジョブの主たる責務はサマリ報告と reflect 判定にある）。
  3. **reflect しきい値判定**（判定根拠は `journal/index.jsonl`＝1 周 1 行の機械可読ジャーナル）: `index.jsonl` の総行数 `T` と当日分の行数 `t` を数え、`N = reflect.every_n_cycles`（既定 10）として **`floor(T / N) > floor((T − t) / N)`**（＝当日の周回で N の倍数を跨いだ）場合、または同種 bad の `recurrence ≥ 2`（reflect スキル既定）が観測される場合**のみ** `/claude-flywheel:reflect` を起動する。`index.jsonl` が無ければ倍数判定はスキップし、bad 再発条件のみ評価する。条件を満たさなければ reflect は起動せず、その旨を報告する（reflect は毎周回さない既存の起動タイミング規律を踏襲）。

### 6. 登録内容の報告

- 読み込んだ cadence 設定（既定値使用の有無・欠落フィールド）、初回 run-cycle の結果、登録した cron ジョブ一覧（run-cycle 定期便の cron 式・ID、締めジョブの発火時刻・ID）をまとめて報告する。

## 出力

- cadence 設定の読み込み結果（既定値使用の有無・欠落フィールドの明示）。
- 初回 `run-cycle` のサイクルレポート。
- 登録した cron ジョブ一覧（run-cycle 定期便・締めジョブそれぞれの cron 式または発火時刻・ID）。

## 注意

- **launchd（OS スケジューラ）／クラウド routine（`/schedule`）は使わない**（検討済みの不採用案。夜間自走が必要になったら再検討する。理由は upstream の要件チケットと `docs/architecture.md` §7 を参照）。
- 本スキルは**セッションが生存している間だけ**自走する。停止・再開時の挙動、および永続的に止める手順（CronList → `flywheel-` プレフィックス検出 → CronDelete）は本文冒頭の注記（セッション内 cron 方式の採用理由）を参照。
- reflect の起動は締めジョブ経由のみに限定する（毎周は回さない。`reflect` スキルの起動タイミング規律と一致させる）。
- **ハーネス自体（skill/サブエージェント/ブリーフ）の改修は本スキルの範囲外**（`reflect` に委ねる）。
- 秘密情報を cron のプロンプト・報告に含めない（`run-cycle` 本体の原則を踏襲）。
- 同一ワークスペースでの再実行に対しては、**手順3冒頭の既存ジョブ掃除が必須**（best-effort ではない。掃除→再登録で冪等になる）。手順2の初回 `run-cycle` は再実行のたびに走るが、`run-cycle` 自体がステータス駆動で冪等・`.flywheel/cycle.lock` が並走を排他するため安全。
