# 実行時テキストと docs の書き分け

> **対象**: 本リポジトリの `skills/`（スキル本文）と `templates/`（利用先へ scaffold する雛形）。
> **目的**: 実行時にモデルへ配送されるテキストと、人間が読む設計ドキュメントの役割を分け、
> **実行時テキストから `docs/` を参照しない**ことを規約として固定する（[#117](https://github.com/masanami/claude-flywheel/issues/117)）。
>
> 判定軸は上流ハーネス（claude-harness `docs/plugin-path-conventions.md` (h)(f)）と同じ。
> 適用面だけが違う（harness は `skills/` `agents/`、flywheel は `skills/` `templates/`）。

## 1. 面の区別

| 面 | 誰が読むか | 残すもの | 置かないもの |
| --- | --- | --- | --- |
| `skills/` `templates/` | **実行時にモデルへ配送される** | モデルの**行動を変える文** — 何をするか／してはいけないか／どう判断するか／契約（ステータス名・exit code・出力書式）／**その形でなければ壊れる理由** | **行動を変えない補足** — Issue・PR・ADR の番号、出典、`docs/` へのポインタ、「〜が決定しており」といった宣言の経緯、用語の言い換え、読み手が既に知っている前提の再説明 |
| `docs/`・`contracts/`・スクリプト内コメント・PR 本文・コミットメッセージ | 人間 | 理由・経緯・番号・比較検討・却下した代替案 | — |

## 2. 判定軸

> **この文を削ると、次に読むモデルの振る舞いが変わるか。**

変わるなら実行時テキストに**インラインで書き切る**。変わらないなら人間が読む面へ置き、実行時テキストには書かない。

**判定軸は「ID や番号を使っているか」ではない。**「`docs/` まで遡らないと意味が取れないか」で決める。ID をラベルとして使い、意味をその場にインラインで書いてあるなら問題ない（例: `【承認ゲート FR-13】` に続けて承認対象・保留の仕方がインラインで書かれている形）。

## 3. なぜ `docs/` を参照してはいけないか（到達性の問題）

**規範を `docs/` に置いて実行時テキストからポインタを張ると、規範が届かないことがある。しかも失敗が静かに起きる。**

| 面 | 到達性 |
| --- | --- |
| `SKILL.md` 本体 | Skill ツールがコンテキストへ**注入**する。確実に届く |
| `docs/` 配下 | 通常の **Read**。**headless 委譲（`claude -p`）では作業ディレクトリ外**であり、利用側に allow が無ければ**拒否される** |
| `templates/` の scaffold 先 | **`docs/` はそもそも存在しない**（プラグイン内の相対パスは利用先ワークスペースで解決しない）＝到達不能 |

- 「規定の正本は `docs/…` を参照」と書いた行は、**headless では 1 バイトも届かないことがある**。それでも処理は完走するため、規範が欠けたまま動いた事実が誰にも見えない（**失敗が沈黙する**）。
- 参照の方向は **`docs/` → `skills/` `templates/` の一方向のみ許可**（設計文書が実装を指すのは可、逆は不可）。
- 複数スキルが共有すべき実行時コンテンツが生じた場合は、`docs/` ではなく実行時に届く場所（各スキルの本文・`references/`）へ置く。

## 4. この規約は「分量を減らせ」ではない（最重要）

**判定軸は分量ではない。** 同じ規約の**逐語コピーが複数箇所に在ること自体は違反ではない**。

- **規約・手順・停止条件の逐語コピーは残す** — 行動を変えるため。`docs/` へ集約すると、規約が最も必要な文脈（対話相手のいない headless 委譲）で届かなくなる（§3）。
- **その規約が生まれた経緯・番号・言い換えは置かない** — 行動を変えないため。

「重複しているから正本 1 箇所＋参照へ集約する」という読み替えは**採らない**。到達性に反しており、規約が黙って届かなくなる。

### 4.1 例外: 配送経路が変わらない集約は「集約」ではない

上の禁止が守っているのは**分量ではなく到達性**である。したがって、**集約しても規範の配送経路が 1 バイトも変わらない**場合は、この禁止の対象外とする。判定は次の 1 問:

> **その集約によって、規範を受け取る側（とくに headless の子セッション）へ届く文字列が変わるか。**

変わらないなら集約してよい。変わる（届かなくなりうる）なら §4 の本則どおり逐語コピーを残す。

| | §4 が禁じている形 | 4.1 の例外に当たる形 |
| --- | --- | --- |
| 規範を受け取るのは | **子**（headless 委譲先） | **親**（メインセッション） |
| どう届くか | 子が `docs/` を Read する必要がある＝**届かないことがある** | 親が正本を読み、**規範を成果物へ書き下ろして子へ渡す**（委譲ブリーフの本文・スクリプトの出力）＝子への配送は逐語のまま |
| 集約したときの失敗様式 | 規範が欠けたまま子が完走（**沈黙する失敗**） | 親が正本を読めなければ**その場で失敗する**（顕在化する） |

**具体例**（いずれも本リポジトリで実施済み）:

- **スクリプトへ寄せる**: `priority-policy.md` の適用条件の検証は、散文の逐語手順を `scripts/priority-policy-resolve.sh` へ移し、スキル本文は「呼ぶ」と「exit と `report=` の解釈」だけを持つ。スクリプトは **Bash 実行**で届くため Read 権限に依存せず、到達性はむしろ上がる。同型の先行例が `noop-check.rb`（`contracts/cycle-commit-paths.txt` を読んで `commit_path=` として出し直す）。
- **サイクルレポートの文言**: 同じ文言をスキルの手順0 と手順6 の両方に書くと、**2 つのリストは必ずずれる**（片方だけ直る）。文言の正本をスクリプトの出力（`report=`）1 箇所に置き、スキル本文は「その値をそのまま転記する」とだけ規定する。

**この例外を「重複は減らせ」と読み替えないこと。** 例外が成立するのは、**集約先が実行時に確実に届く面**（スクリプトの出力・スキル本文・`references/`）である場合に限る。集約先が `docs/` なら §3 のとおり到達性が壊れるため、配送経路が変わる＝本則が適用される。

## 5. 「理由」は経緯ではない（削る側に倒さない）

「なぜその形か」の理由は、**後続の一括是正が規約を「親切に」書き換えるのを止める**働きを持つ。止められなければ違う実装が出るのだから、理由は**行動を変える文**であり、残す側に落ちる。

見分け方も §2 の 1 問で足りる: その文を消したとき、**次に読むモデルが違う操作を選びうるか**。選びうるなら規範の一部（＝理由）として残す。選ばないなら経緯であり、置かない。

例（本規約の適用時に実際に行った判定）:

- ✗ `**launchd／クラウド routine は使わない**（…理由は docs/architecture.md §7 を参照）` → ✓ 不採用の理由（launchd はセッションが無いため対話承認が使えない／クラウド routine は状態正本がローカルファイルで噛み合わない）を**インラインで書き切る**。理由が無ければ後続のエージェントが「耐久性が上がる」と考えて launchd へ切り替えうる
- ✗ `中断された台帳トランザクションの復旧を先に行う（docs/challenge-ledger-format.md §…）` → ✓ 台帳・アーカイブの実状態から状態を判定する**回収表そのもの**をインラインへ。表が届かないと回収の仕方が決まらない
- ✗ `形式の正本は docs/challenge-ledger-format.md §関連リポジトリ・関連Issue・関連PR` → ✓ ポインタを削除（形式 `<owner>/<repo>#<番号>` と追記規律は同じ行に既にインラインで書かれている）

## 6. 機械が検査できる水準の境界

**この境界を曖昧にすると「テストが緑＝書き分けができている」と読まれる**ため、明示する。

| 要求 | 機械検査 | 強制する主体 |
| --- | --- | --- |
| 実行時テキストに行動を変えない補足が混ざっていないこと | **検査できない**（「行動を変えるか」は文の意味に依存する） | 書く時点の判断／PR レビュー（人間・自動レビューツール） |
| `skills/` `templates/` から `docs/` 配下を参照していないこと | **検査できる** | [`scripts/tests/runtime-text-refs.test.sh`](../scripts/tests/runtime-text-refs.test.sh) |

**検査は拡張子で絞らない**。禁じているのは「`docs/` 配下を指すこと」であり、`.md` だけを見ると `docs/schema.json` や `docs/generated/index.html` のような非 Markdown を足した時点で静かに穴が開く。面の呼称としての素の `docs/`（「人間が読む面 `docs/`」等）はパスではないので誤検出しない。

**禁止語（`Issue #NNN` 等）の不在検査は採らない**。本リポジトリのスキルは Issue 番号・PR 番号を**入力として受け取り**、記入例としても書く（`関連Issue: claude-flywheel#87` 等）ため、語彙で判定するには allowlist が要る。その allowlist は規約本文とは別に維持される**第 2 のリスト**になり、ずれても誰も気付かない。機械で固定するのは `docs/` 参照という**構文的に判定できる 1 点**に絞る。

## 7. 除外の規則（allowlist を作らない）

除外は**ファイル名の列挙ではなく構造**で定める（ファイルの allowlist は第 2 のリストになり、ずれても気付けない）。

| 面 | 除外 | 理由 |
| --- | --- | --- |
| `skills/` | **行全体が HTML コメントである行**（`<!-- … -->` だけの行） | 保守者向けの注記であり、実行時の規範を担わない。**規範は常にコメントの外にインラインで書き切る**（コメントがモデルへ配送されないことは保証された挙動ではないため、「配送されない」側に賭けず「配送されても失われる規範が無い」側で成立させる） |
| `skills/` | 行末に付けた HTML コメント | **除外しない**。規範を書いた行の末尾にコメントを足せば検査を抜けられる、という穴を残さないため |
| `templates/` | **除外なし**（HTML コメント内も違反） | scaffold 先に `docs/` は存在せず、保守者向け注記の置き場としても機能しない（利用先の人間が辿れないポインタになる） |

現在この規則で除外されている実在の行は `skills/reflect/SKILL.md` のミラー同期注記 1 行のみ。テストは**除外した行を毎回出力する**（黙って除外しない）。

## 8. 既存箇所の扱い

`docs/` 参照は §3 のとおり**到達性の問題であり構文的に判定できる**ため、**全数を解消済み**とし、テストで再発を止める（harness (h) の「行動を変えるか」の遵守が前向き適用に留まるのとは扱いが違う——あちらは意味に依存して機械判定できないため）。

一方で、**参照を外すときに規範ごと落とさないこと**は機械では守れない。ポインタの先に**行動を変える内容**があれば、削除ではなく**インライン化**する（§5 の 2 例目）。一括置換で参照だけを機械的に削らない。
