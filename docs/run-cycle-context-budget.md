# run-cycle の文脈コスト実測と、規定の棚卸し（#97 の判断材料）

> **本ドキュメントは #97 の判断材料**（[#97](https://github.com/masanami/claude-flywheel/issues/97)）。
> 「残す／移す／消す」の仕分けと置き場所の候補、到達性リスク、論点を並べる。
> **§1・§2 の実測は 2026-08-27 JST 時点のスナップショット**であり、以後の実装で SKILL.md は
> 変わる（D-2 の初回コミット時点 26,752 tok → **同 PR のレビュー対応で起動失敗経路の規定を足し 26,890 tok** → D-1 実施後 26,516 tok。§3.3 の実測はいずれもマージ済み `main` との差分）。**確定した採否は §6 の各行と §7 に追記する**
> ——未決として起票したものと、確定したものが同じ表で追えるようにするため。
> 仕分けの判定軸は [runtime-text-conventions.md §2](./runtime-text-conventions.md) と同一
> ——**この文を削ると、次に読むモデルの振る舞いが変わるか**。

## 0. 要旨

1. **`run-cycle/SKILL.md` は 1 サイクルの入力文脈の約 1/3 でしかない**（分母は §1.2 の
   **条件付きを含む合計 〜91,000 tok**＝30.4%。毎周・無条件の 63,803 tok を分母に取れば
   **43.3%**）。同じ規模の第二の固定コストが `challenge-ledger.md`
   （**27,913 tok ＝ SKILL.md の 27,652 tok とほぼ同じ**）で、こちらは課題が増えるたびに
   単調増加する。SKILL.md だけを縮めても、達成できる削減は同じ 〜91,000 tok に対して
   **11.5%** で頭打ちになる（§3.2）。
2. **スクリプトへ移した規定は文脈コストがほぼゼロになる**。実測で、正常系のスクリプト出力は
   `heartbeat-check.sh` / `validate-artifact.rb` とも **0 バイト**だった（§1.3）。
   「散文 → スクリプト」は移設ではなく**消去に近い**。
3. 仕分けの結果、151 規定単位のうち **移す 9,417 tok（34%）／消す 1,075 tok（4%）**。
   残り 16,634 tok（60%）は削るとモデルの振る舞いが変わる。
   これに**分類対象外 526 tok（2%・見出し／フロントマター等。内訳は §2.1）**を足して
   SKILL.md 全体 27,652 tok になる（§2）。
4. **`docs/` への退避は採れない**——本リポジトリで既に成文化・テスト強制済み
   （[runtime-text-conventions.md §3](./runtime-text-conventions.md)）。到達性が確保できる
   置き場所は「スクリプト（Bash 実行）」「ワークスペースへ scaffold 済みのテンプレート」
   「memory」「positions」の 4 つ（§3）。
5. **#97 の完了条件 2（許可パスの機械可読な正本）は既に満たされている**。実コードで確認し、
   変異注入で検出されることも確かめた（§4）。

## 1. 実測

### 1.1 計測方法（再現手順）

トークン数は **`tiktoken` の `o200k_base`** で数えた。**Claude のトークナイザではなく、Claude 上での
測定は行っていない**。したがって本ドキュメントの「tok」表記と、そこから導いた比率・順序は
**すべて `o200k_base` 上の比較**であり、Claude のトークナイザでも同じ値・同じ比率になることは
主張しない。バイト数は併記してあるので、別のトークナイザで数え直すことができる。

**それでも結論が壊れにくいと考える理由**（主張ではなく、読み手が自分で確かめられる材料として）:
本ドキュメントが比較している 10 ファイルの**バイト／トークン比は 3.27〜3.50 の範囲に収まる**
（変動幅 ±3.5%）。

| ファイル | B/tok | ASCII 率 |
| --- | ---: | ---: |
| `skills/run-cycle/SKILL.md` | 3.47 | 40% |
| `challenge-ledger.md` | 3.27 | 55% |
| `CLAUDE.md` | 3.45 | 34% |
| `memory/<domain>/INDEX.md` | 3.44 | 60% |
| `challenge-sources.md` | 3.36 | 64% |
| `priority-policy.md` | 3.29 | 34% |
| `skills/ingest-challenges/SKILL.md` | 3.50 | 41% |
| `skills/agent-memory/SKILL.md` | 3.50 | 54% |
| `positions/<domain>.md` | 3.35 | 46% |
| `runtime/README.md` | 3.44 | 57% |

比較対象がこれだけ均質であれば、**同じ結論はバイト数だけからも導ける**（バイト数は
トークナイザに依存しない）。実際 §0 の「SKILL.md ≒ 台帳」も、§3.2 の削減比も、
バイト基準に置き換えて同じ順序になる。**Claude 上で数え直したときに変わりうるのは、
本ドキュメントが提示する tok の絶対値と、上の ±3.5% の範囲を超える差が生じた場合の比率**である。

```bash
python3 -m pip install --user tiktoken
python3 - <<'PY'
import tiktoken; enc = tiktoken.get_encoding("o200k_base")
s = open("skills/run-cycle/SKILL.md", encoding="utf-8").read()
print(len(s.encode()), len(enc.encode(s)))   # => 96080 27652
PY
```

参考の換算係数（`skills/run-cycle/SKILL.md` の実測）: **約 3.47 バイト / トークン**
（96,080 B ÷ 27,652 tok）。他ファイルの実測値は上表を参照。

## 2. 規定単位の仕分け

判定軸は [runtime-text-conventions.md §2](./runtime-text-conventions.md)。
**分量ではなく「削るとモデルの振る舞いが変わるか」**で決めた。同§4 のとおり
「重複しているから 1 箇所へ集約」という理由では移していない——移した根拠は
(a) 判定が決定的でスクリプトに落とせる、(b) その周に必要ない（段階ロード）、
(c) 同一ファイル内の逐語重複・却下した代替案、のいずれかである。

### 2.1 分類対象外の 526 tok（SKILL.md 全体との差分）

上表の合計 27,126 tok と SKILL.md 全体 27,652 tok の差 **526 tok** は、仕分けの単位を
**箇条書きブロック（ハイフン + 空白で始まる行と、その継続行）**に取ったことによる対象外分である。
内訳（行単位で数え直した実測）:

| 区分 | tok |
| --- | ---: |
| 見出し（`#` / `##` / `###`） | 251 |
| フロントマター（`name:` / `description:` / `---`） | 107 |
| 冒頭の引用注記（`>` 行） | 90 |
| 本文リード文（「Flywheel の 1 周…」） | 67 |
| 行単位の小計 | **515** |
| 全体からの差分との誤差（BPE の行境界効果） | 11 |
| **差分の合計** | **526** |

行を個別にトークン化した合計（515）と、文書全体をトークン化した差分（526）が 11 tok ずれるのは、
BPE が改行を隣接トークンへ併合するためで、切り出し方の違いによる誤差である。

この 526 tok は**削減対象にも維持対象にも数えていない**（見出し・フロントマターは
構造そのもの）。§3.2 の「27,652 → 17,160」は **残す 16,634 ＋ 分類対象外 526** と一致する。

## 3. 置き場所の候補と到達性リスク

到達性を測らずに集約すると、**規範が 1 バイトも届かないまま処理だけ完走する**（失敗が沈黙する）。
[runtime-text-conventions.md §3](./runtime-text-conventions.md) が `docs/` について定めたのと
同じ検査を、候補ごとに行った。

| # | 候補 | 到達性 | 根拠 | リスク |

### 3.1 「委譲ブリーフ定型」は §4 の禁止に当たるか（重要な区別）

[runtime-text-conventions.md §4](./runtime-text-conventions.md) は
**「重複しているから正本 1 箇所＋参照へ集約する」という読み替えは採らない**と定めている。
Issue #97 の提案 3（手順3 の定型をテンプレート化）はこれに抵触するように見えるが、**配送経路が違う**:

| | §4 が禁じた形 | 手順3 の委譲ブリーフ定型 |
| --- | --- | --- |
| 規範を受け取るのは誰か | **子**（headless 委譲先） | **親**（メインセッション） |
| どう届くか | 子が `docs/` を Read する必要がある＝**届かないことがある** | 親がテンプレートを読み、**ブリーフ本文へ書き下ろして stdin で子へ渡す**＝子への配送は逐語コピーのまま変わらない |
| 集約したときの失敗様式 | 規範が欠けたまま子が完走（沈黙する失敗） | 親がテンプレートを読めなければ**ブリーフを組み立てられない**＝親の側で顕在化する |

つまり手順3 の定型を (c) の経路でテンプレート化しても、**子への到達性は 1 バイトも変わらない**。
これは §4 が想定した事例と異なる。ただし §4 の文面は無条件の禁止として読めるため、
**この区別を規約として認めるかどうかは未決（D-3）**とする。

## 4. 完了条件 2 の充足状況（実コードによる判定）

> 完了条件 2: 少なくともサイクルコミットの許可パスが機械が参照できる正本を持ち、
> no-op 判定など他の機構がそれを参照できる（PR #96 の P1 が構造的に再発しない）。

**判定: 満たされている。** 根拠:

1. **正本が存在し機械可読**: [`contracts/cycle-commit-paths.txt`](../contracts/cycle-commit-paths.txt)。
   `[commit]` / `[exclude]` の 2 セクション形式で、セクション外の行と空の `[commit]` は
   **判定不能（exit 2）** になる（`scripts/noop-check.rb` の `load_paths_file`）。
2. **no-op 判定が参照している**: `noop-check.rb` は同ファイルを読み、
   dirty パスを `[commit]` → `reason=state-dirty` ／ `[exclude]` → 無視 ／
   **どちらでもない → `reason=out-of-scope-dirty`** に 3 分類する。
   監視範囲は**ワーキングツリー全体**であり、列挙から漏れたパスは
   「変化なし」側ではなく `out-of-scope-dirty` 側へ落ちる（fail-closed）。
   **これが PR #96 の P1（監視パスが許可パスより狭い）を構造的に潰している部分**である。
3. **コミット側も同じ正本から導かれる**: `noop-check.rb` は `[commit]` を
   `commit_path=<path>` として stdout に出し直し、SKILL.md 手順6 は
   「その値をそのまま使えばよい〔判定を実行できなかった周は正本ファイルを直接読む〕」と規定する。
   `git add` の pathspec と分類が同一の出典を持つ。
4. **テストで固定されている**: `scripts/tests/noop-check.test.sh` が
   (i) `commit_path=` 出力と正本の `[commit]` の**完全一致**、
   (ii) 正本の各 `[commit]` パスが SKILL.md 本文に現れること、を検査する。

### 4.1 変異注入による確認

正本の `[commit]` から `positions` を 1 行削り（SKILL.md 側の列挙は残したまま＝片方向のずれ）、
テストを実行した:

```text
passed: 137 / failed: 1
FAIL - 許可パスに positions が含まれる（実運用のサイクルコミットに現れる）
```

**検出された。** ただし検出したのは構造的な双方向検査ではなく、
**`positions` を名指しした 1 本のアサーション**である。すなわち「正本に無いパスが
SKILL.md 側にだけ残る」ずれは、そのパスを名指しするアサーションが**書かれている限りで**
検出される。パスを新規追加したときにアサーションを書き忘れると穴が開く
（正本ファイル冒頭のコメントが「追加・削除したらテストも同時に更新すること」と
運用規律で補っている状態）。これは `sync-free-invariant` が言う第2のリストに当たるが、
**置き場所がテストである**点で許容範囲とも読める。強化するかは未決（D-5）。

### 4.2 残る非対称

- SKILL.md 手順6 の本文には許可パスの**インライン列挙**（`challenge-ledger.md` / `challenge-archive.md` /
  `memory` / `journal` / `positions`）が残っている。正本ではない旨は明記されているため
  動作には影響しないが、`sync-free-invariant` の観点では第2のリストである。
- `commit_path=` は `emit_and_exit` で常に出力されるが、`COMMIT_PATHS` が埋まる**前**に

  SKILL.md の「判定を実行できなかった周は正本ファイルを直接読む」がこの穴を塞いでいる。

## 7. #97「一般原則」5 項目に対する所見（採否は未決）

| # | 原則 | 所見 |
| --- | --- | --- |
| 1 | 「放っておくと間違えること」だけ書く。判定基準は**観測された失敗の回数**。1 回も起きていない予防的規定は書かない | **条件を広げて採用（確定）**。原案のままでは [runtime-text-conventions.md §2](./runtime-text-conventions.md) の軸（「**削るとモデルの振る舞いが変わるか**」）と食い違い、まだ 1 回も起きていないが起きたら**不可逆**な失敗（本番反映・データ消失）を止める規定が削除対象になる——実際、手順0 の台帳トランザクション回収表は**消失が起きる前**に書かれている。そこで判定軸を「**観測された失敗、または不可逆な失敗の予防**」へ広げたうえで採用する。以後の改訂はこの軸で判断する |
| 2 | 決定的に検査できるものは散文でなくコードへ。散文に残すのは「いつ呼ぶか」と「結果の解釈」だけ | **実測が支持する。** 正常系のスクリプト出力は 0 バイト（§1.3）で、移設ではなく実質消去になる。本ドキュメントの「移す」9,417 tok のうち約 6,500 tok がこの原則によるもの |
| 3 | 分岐・列挙は散文でなく構造（表）で。表は行の完全性をテストで固定できる | **支持する。** ただし**トークン削減効果は小さい**（同じ情報を表にしても 2〜3 割減程度）。効果は分量ではなく**テストで固定できること**（`prose-spec-invariant-tests`）にある。原則 5 と並べると「分量のため」と誤読されうるので、目的を書き分けたい |
| 4 | 規定には理由を 1 行添える。ただし経緯は journal / memory / Issue へ | **既に成文化済み**（[runtime-text-conventions.md §5](./runtime-text-conventions.md)「理由は経緯ではない（削る側に倒さない）」）。本項は再掲であり、新規に採る／採らないの対象ではない。**両者が併存すると第2のリストになる**ため、参照へ寄せるのが望ましい |
| 5 | 長さは「1 回の実行で読む量 × 頻度」で測る | **支持するが、適用範囲が狭い。** #97 は run-cycle の SKILL.md にこの物差しを当てているが、同じ物差しを当てるべき対象は台帳（27,913 tok・毎周）・memory INDEX（3,860 tok・毎周）・`ingest-challenges/SKILL.md`（7,888 tok）も同じである（§1.2）。原則としては「毎周ロードされるすべてのファイル」に一般化するのが自然 |
