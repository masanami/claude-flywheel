# 拍動停止の検知 — 最小緩和の設計と根本方式の選択肢（Issue [#83](https://github.com/masanami/claude-flywheel/issues/83)）

> **ステータス**: §2（最小緩和）は実装済み。§3（セッション寿命に拍動を紐づけない方式）は**選択肢の比較まで**であり、**採否は人間判断（未決）**。本ドキュメントを読んだエージェントが §3 の実装へ自律的に進んではならない。

## 1. 背景（何が起きたか）

2026-08-06 から 2026-08-11 までの 5 日間、`run-cycle` が 1 周も起動しなかった（0.15.0 時点の実害報告）。その間、未終了の委譲（`delegate_end` の無い `delegate_start`）が放置され、人間が次に触れるまで誰も気づけなかった。

構造的な弱点は 3 段:

1. セッション内 cron は**セッションを閉じると消える**（採用済みの仕様。[architecture.md §7](./architecture.md)）。
2. したがって `start-day` を**毎朝人間が起動する運用**が前提になる。
3. しかし**起動を忘れたことを検知する仕組みが無かった**ため、「止まっている」こと自体に気づけない。`log-run-event.sh check` は未終了 `*_start` を検出できるが、それを回す `run-cycle` 自体が止まっていた——「検算の仕組みはあるが、拍動が無いと働かない」。

## 2. 実装済みの最小緩和（スキーマ変更なし）

**方式**: `run-cycle` 手順0 の最初（ロック取得より前）で、`scripts/heartbeat-check.sh`（読み取り専用）が `runs.jsonl` の最終 `cycle_end` からの空白期間を検査し、しきい値超過なら**警告＋未終了 `*_start` の件数・該当行**をサイクルレポートに出す。`start-day` 経由なら初回 run-cycle がこの検査を行い、警告は start-day の最終報告の**冒頭**にも掲げる。

これは「止まらなくする」仕組みではなく「**止まっていたことに、次に人間が触れた瞬間に気づける**」仕組み（空白期間の可視化）。拍動そのものの耐久化は §3 の論点。

### 設計判断（と、その根拠）

| 判断 | 内容 | 根拠 |
| --- | --- | --- |
| しきい値の単位は**営業日** | 最終 `cycle_end` の日付と本日の**間に挟まる**営業日（`cadence.json` の `business_days`・既定 `1-5`）が `heartbeat.stale_after_business_days`（既定 1）以上なら警告 | 固定時間（例: 24h）だと金曜終業→月曜朝の正常な週末で毎週誤警報になる。Issue の提案「業務日ベースで1日以上」に対応 |
| 検査は**ロック取得より前** | run-cycle 手順0 の最初の動作とする | ロック取得（`cycle-lock.sh acquire`）は stale ロック回収時に前周の `cycle_end`（`abandoned`）を**現在時刻で代筆**する。取得後に検査すると「前周クラッシュ→数日放置」という本検知が最も拾うべきパターン（#83 の実害そのもの）が代筆でマスクされる |
| **検査不能≠0件** | `runs.jsonl` 不在・読み取り不可・`cycle_end` 未記録は exit 2（検査不能）とし、「空白なし・正常」と読み替えない | fail-open にすると「検知の仕組みはあるが検知できていない」という #83 と同型の穴が再生産される。`log-run-event.sh check` の「不在 = exit 0＋警告」より安全側（本検知の目的が「止まっていることに気づく」ことそのものであるため） |
| 警告のみ・サイクルは止めない | 検知結果（exit 1/2）にかかわらずサイクルは続行する | 観測が制御を阻害しない、という runs.jsonl 系の既存原則。未終了 `delegate_start` の回収は手順6 の既存の検算・事後補記が担う（責務を重複させない） |
| 既定 ON | `heartbeat` ブロックが cadence.json に無くても既定値（営業日 1 日）で検査する | opt-in にすると「宣言していないワークスペースでは止まっても気づけない」＝ #83 の失敗様式の再生産。検査は読み取りのみでコストが無いため、periodic-audit（LLM fan-out でコスト大→opt-in）とは逆の既定を選ぶ |
| 拍動 = `cycle_end` イベント | `result` が `completed` / `abandoned` いずれも 1 拍と数える | Issue の提案どおり「最終 `cycle_end` からの経過」を採用。`abandoned` の代筆は生きているサイクルの回収時に行われるため、直後に本物の `cycle_end` が続く（拍動としての意味は保たれる） |

### 既知の制限（意図した割り切り）

- **同日内の停滞は検知しない**（朝に 1 周だけ回って止まった等）。対話割り込みによる発火遅延（正常動作）と区別できず、間隔ベースのしきい値は誤警報源になるため。日単位の空白（#83 の実害）に絞る。
- **検知の実行主体は依然 run-cycle**。拍動が完全に止まっている間は本検知も走らない（次に start-day / run-cycle が起動された瞬間に空白を報告する事後検知）。リアルタイム検知は §3 の領分。

## 3. 根本的な再検討: セッション寿命に拍動を紐づけない方式（採否は人間判断・未決）

「日次の手動起動＋セッション内 cron」という現行モデルの再検討。launchd / クラウド routine が[不採用になった経緯（architecture.md §7）](./architecture.md)は把握したうえで、「止まったことに気づけない」実害が当初想定より大きい、という #83 の指摘を受けた選択肢の整理。

**論点の分解**: 「拍動を止まらなくする」（駆動の耐久化）と「止まったら気づける」（検知の外部化）は別の問題であり、後者だけなら §7 の不採用理由に抵触せずに解ける余地がある。

| # | 選択肢 | 概要 | 利点 | 難点・§7 不採用理由との関係 |
| --- | --- | --- | --- | --- |
| A | **現状維持＋§2 の緩和のみ** | 事後検知のみ。次に人間が触れた時点で空白に気づく | 追加コストゼロ。§7 の判断と完全整合 | 空白期間そのものは生じ続ける（気づくのが早くなるだけ）。「放置されがち」という運用実感は解消しない |
| B | **観測プレーン（board）に停止検知・通知を追加** | board は既に `runs.jsonl` を読む読み取り専用プレーン。最終 `cycle_end` がしきい値超過のエージェントを画面上で警告（＋通知） | 観測プレーンの許容条件（書き込まない・制御の依存にならない）に収まり、**§7 の不採用判断を一切覆さない**。fleet 全エージェントを横断で見張れる | board を開いていなければ気づけない（board 自体の生存にも依存＝検知の完全性は無い）。claude-flywheel-board 側の実装＝**横断（複数 repo）課題**になる |
| C | **OS スケジューラ（launchd 等）で「検知・通知だけ」行う軽量 watchdog** | 拍動の駆動はセッション内 cron のまま。launchd は 1 日 1 回 `heartbeat-check.sh` を実行し、stale なら OS 通知等を出すだけ（claude セッションを起動しない） | 止まっていても人間の起動なしで気づける（検知の完全性が最も高い）。承認ゲート・サブスク消費・対話承認の問題（launchd 不採用の主因）は**駆動を移さないため生じない** | ホストごとの launchd 設定という新しいセットアップ面（fleet 各ホストで管理）。通知手段（macOS 通知・メール等）の選定が必要。§7 の「launchd で拍動」不採用とは別物だが、OS 依存の管理物が増える点は同系の負担 |
| D | **クラウド routine で「検知・通知だけ」行う watchdog** | `/schedule` の定期エージェントが、エージェント repo の push 履歴（journal は Git 追跡・毎周コミット）から最終サイクル日時を読み、stale なら通知 | ホスト・セッションの生存に一切依存しない検知 | `runs.jsonl` はローカル（gitignore）のためクラウドから読めず、**journal の push を正とする間接検知**になる（push 忘れ・ローカル運用と乖離）。§7 の「クラウド routine で拍動」不採用理由（ローカル状態と噛み合わない）が検知でも部分的に残る |
| E | **launchd 等で拍動そのものを駆動**（headless `claude -p "/run-cycle"`） | 日次手動起動の前提自体を廃止 | 起動忘れが構造的に消える | §7 で不採用にした論点が全面的に再燃する（対話承認が使えない・「人間コミットの `[x]`」経路の実運用検証・サブスク消費の制御・即時停止のしにくさ）。再検討トリガー「夜間・無人時間帯の自走が必要になったとき」には未達 |

**提案（実装者としての推奨・拘束力なし）**: B（board への停止検知）を第一候補、C（launchd の検知専用 watchdog）を補完候補とする。いずれも「駆動はセッション内 cron・検知だけ外部化」という分解に基づき、§7 の不採用判断を覆さずに「気づけない」問題だけを解ける。B は横断課題（claude-flywheel-board リポジトリ）として別途起票が必要。E は §7 の再検討トリガー成立まで見送りを維持するのが一貫する。
