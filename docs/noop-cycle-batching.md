# no-op 周の軽量化 — コミットだけを変化のあった周にまとめる（Issue [#82](https://github.com/masanami/claude-flywheel/issues/82)）

> **ステータス**: 実装済み。判定の参照実装は [`scripts/noop-check.rb`](../scripts/noop-check.rb)、呼び出し規定の正本は [run-cycle SKILL.md](../skills/run-cycle/SKILL.md) 手順6。

## 1. 背景と、実データによる費用対効果の再評価

### 起票された観測（[#82](https://github.com/masanami/claude-flywheel/issues/82) の報告。**別ワークスペース由来の可能性があり本リポジトリからは追検証できない**）

> 自走を 1 日回したところ、5 周のうち 4 周が完全な no-op（`touched_issues` が空）だった。前進可能な課題がすべて人間の承認ゲート（FR-13 / FR-32 / FR-22）で止まっており、変化ゼロの周でも `.md` 生成・`index.jsonl` への 1 行 append・Git コミットが発生して、**Git 履歴が観測ノイズで埋まり「実際に何かが動いた周」を見つけにくくなる**（観測日 2026-08-13 に cycle-2〜cycle-5 の 4 ファイル＋4 コミット）。

### 参照ワークスペースの実測（本ドキュメントが「20/20 周」等の根拠に使っているワークスペース）

| 項目 | 実測 |
| --- | --- |
| 2026-08-13 の journal | **Git 履歴上に一度も存在しない**（`git log --all --diff-filter=A -- journal/*.md`）。同日のコミットは `flywheel-init` の scaffold・ポジション定義・エージェント名設定＝**セットアップ日**で、run-cycle は 1 周も回っていない |
| cycle-2〜cycle-5 が揃う日 | 2026-08-14。その 4 周の `touched_issues` は 4 / 1 / 3 / 3 件（`delegations` 0 / 1 / 2 / 3、`pr_urls` 0 / 1 / 2 / 3）＝**no-op ではない** |
| 全 20 周のうち §4 の条件 2・3・4 を満たす周 | **1 周のみ**（2026-08-14 seq 1・初回サイクル） |

したがって**起票時の観測は本ワークスペースの履歴と一致しない**（別エージェントのワークスペース由来である可能性を排除できていない）。本ドキュメントは起票内容を報告として引用するに留め、費用対効果は実測で評価する。

### 発火率の見積もりと、それでも入れる理由

条件 1・5・6・7 は Git 履歴から再現できないため、条件 2・3・4 だけで測った **1 / 20 周が発火率の上限**（実際はこれ以下）。「4/5 周のノイズを削る」という起票時の前提は、少なくともこのワークスペースでは成立しない。

それでも採用するのは、**発火率が「エージェントが承認ゲートで完全に塞がっている割合」そのもの**だからである。参照期間（2026-08-14〜20）はほぼ全周で実作業が進んでおり塞がる周が無かった。起票された「5 周中 4 周が承認待ちで塞がった日」は、この機構が効く状態の報告であり、**塞がる日が来たときにだけ効く保険**として意味を持つ。加えて本機構は:

- 契約物（スキーマ・バリデータ・フィクスチャ）の変更が**ゼロ**で、消費者への影響も**ゼロ**（§2・§3）
- 発火しない周のコストは判定スクリプト 1 回の実行のみ
- 判定が壊れても fail-closed（従来どおり毎周コミット）に縮退する（§4）

**入れ得の側に倒れているが、「履歴のノイズが劇的に減る」と期待すべきではない**——これが実データに基づく正直な評価である。

**単純に「書かない」ではズレる**——`index.jsonl` の行数は複数の消費者の入力になっている（§2）。

## 2. 消費者への影響（実コードで確認した事実）

`index.jsonl` を読む消費者は 3 者。いずれも**Git のコミットではなくワーキングツリー上のファイルを読む**。

| 消費者 | 読み方（実装） | 行数・スキーマへの依存 |
| --- | --- | --- |
| `start-day` の締めジョブ（reflect しきい値判定） | [start-day SKILL.md](../skills/start-day/SKILL.md) 手順5-3: 総行数 `T` と当日分 `t` を数え `floor(T / N) > floor((T − t) / N)` | **行数に強く依存**。no-op 周の行を落とすと周回カウントがズレる |
| `reflect` | [reflect SKILL.md](../skills/reflect/SKILL.md): `pending_approvals` の頻発ゲート・`delegations` の失敗傾向を集計する追加入力 | フィールドの形に依存（行数そのものは締めジョブ側の判定に使われる） |
| claude-flywheel-board のパーサ | `src/server/parsers/journal.ts` の `parseJournal`（行ごとに JSON.parse → 全 7 フィールドを型検証。`deriveLogEntries` は `touched_issues[].id` と `pending_approvals[].issue` を課題 ID で突き合わせる） | **全 7 フィールド必須の形に依存**。ファイルパスは `watcher.ts` の `JOURNAL_FILE_NAME = journal/index.jsonl` を chokidar で監視。**`.md` は一切読まない** |

**確認できた重要な性質**:

- 3 者とも `index.jsonl` を**ファイルとして読む**（journal の履歴を `git log` から読む消費者はいない）。したがって**コミットの粒度を変えても消費者の入力は 1 バイトも変わらない**。
  - なお `git log` を読む箇所は run-cycle 全体には 2 つある（[run-cycle SKILL.md](../skills/run-cycle/SKILL.md) 手順1 の承認の真正性＝`challenge-ledger.md` の author 確認／[challenge-ledger-format.md](./challenge-ledger-format.md) の完了 30 日の基準日特定）。**いずれも対象は台帳の履歴**で、台帳に未コミット差分があれば条件 1 が必ずコミットさせるため、台帳のコミット粒度は束ねの影響を受けない。
- board のパーサは JSON オブジェクトの**追加フィールドを拒否しない**（`validateJournalEntry` は必須フィールドの型だけを見る）が、契約側のスキーマ（[`contracts/schemas/journal-index.schema.json`](../contracts/schemas/journal-index.schema.json)）は `additionalProperties: false` のため、フィールドを増やす案は**バリデータで違反**になる。
- run-cycle 手順6 の `validate-artifact.rb journal-index --tail 1 --expect-cycle <当周>` は「当周に append した 1 行が当周のもの（`date`・`seq` 一致）であること」を証明する。**毎周 1 行 append される前提**の上に立っている。

## 3. 3 案の比較

| # | 案 | スキーマ／1:1 対応 | `--tail --expect-cycle` | reflect / start-day の行数 | board | ノイズ削減 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | no-op 周は `.md` を生成せず `index.jsonl` に 1 行だけ残す | **1:1 対応が崩れる**（`journal-md` 検査と board のセクション対応の前提）。`date`/`seq` から `.md` 名を導けない行が生まれる | 維持できる | 維持できる | 直接の破綻はない（`.md` を読まないため） | **不十分**（`.md` は減るが `index.jsonl` の append とコミットは毎周残る＝**履歴のノイズは減らない**） | **不採用** |
| 2 | 連続 no-op を 1 エントリに集約（`seq` 範囲＋回数） | スキーマ変更（新フィールド）。集約のたびに**末尾行を書き換える**＝ `index.jsonl` の append-only 不変条項に違反 | **破綻**（末尾行が「当周の 1 行」でなくなる） | **破綻**（1 行＝ N 周になり、行数カウントを重み付き集計へ変更する必要） | **破綻**（`additionalProperties: false`・board の追随が必須） | 大きい | **不採用** |
| 3 | 記録は現状どおり毎周行い、**コミットだけ**を変化のあった周にまとめる | **無変更** | **無変更**（保留分を含むコミットでは `--tail` を広げるだけ。`--expect-cycle` の意味論は同じ） | **無変更** | **無変更** | 目的そのもの（履歴のノイズだけを削る） | **採用** |

**採用根拠**: 問題は「記録が多いこと」ではなく「**Git 履歴に変化ゼロのコミットが並ぶこと**」である。案 1 は問題の所在（コミット）を外しており、案 2 は 4 つの契約（スキーマ・append-only・同一性証明・行数カウント）すべてを同時に壊す。案 3 は**契約物の変更をゼロ**にしたまま目的を達成する。起票者の推奨とも一致する。

**案 3 が持ち込む唯一の新しいリスクは「未コミットの成果物がワーキングツリーに滞留すること」**で、これは §5 の 2 つの上限で抑える。

## 4. 「変化なし（no-op）」の機械的定義

判定の正本は [`scripts/noop-check.rb`](../scripts/noop-check.rb) 冒頭のコメント。**次の 7 条件がすべて成立したときだけ no-op**（1 つでも欠ければコミットする＝ fail-closed）。

| # | 条件 | 何を防ぐか |
| --- | --- | --- |
| 1 | **ワーキングツリー全体**に未コミットの差分が無い（追跡・未追跡とも。journal と `[exclude]` 宣言済みパスを除く） | 「許可パス内の変更がコミットされない」＋**パス集合の列挙漏れ**（下記） |
| 2 | 当周の `index.jsonl` 行の `touched_issues` / `delegations` / `pr_urls` が**すべて空** | ステータス遷移・委譲・PR 作成の取りこぼし |
| 3 | `pending_approvals` の **(gate, issue) 集合が前周の行と一致**する | 承認待ちの**新規発生・解消**（ステータス遷移を伴わない FR-22 ゲート等） |
| 4 | 当周の `.md` の**構造が契約どおり**（定型 5 セクションが過不足なく揃い、閉じない HTML コメントが無い）で、①触った課題 ②委譲 ③PR・ブランチ URL ④承認待ちゲート一覧 に**「該当なし」の宣言以外の記載が無い** | `.md` と `index.jsonl` の 1:1 の食い違い（`.md` にだけ書かれた変化）。**構造が崩れていれば判定不能**（見出しのずれ・閉じないコメントで対象セクションを見失い、条件4 が空虚に真になるのを防ぐ） |
| 5 | 当周の `runs.jsonl`（**`--anchor-after-line` で位置指定した当周の `cycle_start` 以降**）に `cycle_start` / `cycle_end` **以外のイベントが無い** | 委譲・差し込み・`delegate_end` の事後補記の取りこぼし（journal への記録漏れがあっても捕捉する裏取り） |
| 6 | `--notable` が 1 件も渡されていない | 機械で検出できない特筆事項（heartbeat 警告・periodic-audit 起動 等。列挙は手順6 が正本） |
| 7 | 未コミットの journal `.md` が**当周と同じ日付のものだけ** | 保留の無限延長（§5） |

### `decisions`（⑤判断と根拠）を判定に使わない理由

run-cycle は**変化ゼロの周でも必ず何らかの判断を書き残す**（実運用ワークスペースの 20/20 周で `decisions` が非空。初回サイクルの「ソース宣言が無いため ingest スキップ」すら記録される）。したがって `decisions` は「変化の信号」として機能せず、判定に含めると本機能は**一度も発火しない**。`decisions` に載る事象のうち「変化」に当たるものは条件 1〜6 のいずれかが捕捉し、機械で捕捉できないものは条件 6（`--notable`）が受け持つ。

### 「該当なし」の宣言をどう認めるか

条件 4 は、行が **`なし` で始まり、続きに数字（半角・全角）も `http` も含まない**ときだけ「該当なし」の宣言と認める。

- **完全一致（`なし` のみ）にできない理由**: 実運用ワークスペースの真の no-op 周（2026-08-14 seq 1・初回サイクル）は `- なし（台帳に課題エントリなし）` と理由を括弧書きで添えており、完全一致だと**本当に no-op の周でも常に「変化あり」になり本機能が発火しない**（`decisions` を判定に含めた場合と同じ失敗様式）。
- **単純な前方一致にもできない理由**: `- なし（C-035 は完了しアーカイブ済み）` / `- なし（前周の session s1 を --resume で継続）` / `- なし（新規作成なし。既存 PR https://github.com/x/y/pull/1 に push）` / `- なし（FR-22 は解消）` のように**括弧の中へ実際の変化を書く**形が素通りする。実運用の journal は既に理由付き括弧書きを常用しており、そこへ ID や URL が滑り込むのを止めるものが無い。
- **数字と `http` を禁じるだけで足りる理由**: ①〜④に書かれる実際の記録は課題 ID（`C-035`）・ゲート名（`FR-22`）・PR 番号（`#161`）・URL・session_id・日付のいずれかであり、**すべて数字か `http` を含む**。キーワード表を持たずに（＝表の取りこぼしを作らずに）塞げる。上の 4 例はすべて検出される一方、`なし（台帳に課題エントリなし）` は宣言として通る。
- `特になし` のように `なし` で始まらない言い回しは（安全側に）変化として扱う。

### パス集合の列挙漏れを構造的に防ぐ

条件 1 の監視対象は**ワーキングツリー全体**で、「サイクルコミットの許可パス」の列挙ではない。許可パスだけを見る設計は、列挙から漏れたパス（`positions/`・`repos.tsv`・`CLAUDE.md`・`challenge-sources.md`・`.flywheel/cadence.json` 等。実運用のサイクルコミット `ead58b1` は `positions/harness.md` を含む）の変更が**黙って「変化なし」側へ落ちる**ため採らない。

dirty なパスは [`contracts/cycle-commit-paths.txt`](../contracts/cycle-commit-paths.txt)（**パス集合の単一正本**。run-cycle 手順6 の `git add` / pathspec もここから導く）で 3 分類する:

| 分類 | 扱い |
| --- | --- |
| `[commit]` | `reason=state-dirty`（コミット） |
| `[exclude]` | 判定に影響させない（`priority-policy.md`＝専用コミット規定・`.flywheel/` のローカル実行状態） |
| どちらでもない | `reason=out-of-scope-dirty`（コミットしたうえで、正本の見直しか人間の作業中かをサイクルレポートで知らせる） |

**新しいパスが増えても既定で「変化あり」側に落ちる**ため、正本の更新漏れは「静かな取りこぼし」ではなく「うるさい通知」として現れる。

### fail-closed の徹底

- **判定不能（exit 2）は「変化あり」と同じに扱う**（コミットする）。`runs.jsonl` 不在・`index.jsonl` の末尾行が当周でない・スキーマ違反・git 実行不能などが該当する。
- **スクリプトの起動自体の失敗（exit 126/127＝ruby 未導入）も判定不能**。ゲートが効かない環境では**従来どおりの毎周コミット**へ縮退する（[contracts/README.md](../contracts/README.md) §実行環境の前提と同じ縮退規律）。
- **保留してよいのは exit 0 のときだけ**。「実行しなかった」「読めなかった」を「変化なし」に読み替えない。
- **判定より後に判明する事象**（検算の exit 2・未終了 `*_start` の検出）は、手順6 の「保留の取り消し条件」が後段で上書きする。
- **判定を行っていない経路が exit 0 を名乗らない**: `--help` も exit 2 で返す（exit code だけで分岐する呼び出しが「保留可」と読まないため）。
- **予期しない例外も exit 2 へ落とす**: 未処理例外は Ruby 既定の exit 1＝契約上の「変化あり」に化け、`decision=`・`reason=` の無い出力を呼び出し側が根拠として転記することになる。不正 UTF-8 は兄弟スクリプト `validate-artifact.rb` と同じく `valid_encoding?` で判定不能に分離する。
- **当周の範囲が一意に決まらなければ判定不能**: 同名 `cycle_start` が 2 本ある（クラッシュ後のサイクル名再利用）状態で `--anchor-after-line` が無ければ exit 2。最後の一致を採ると 2 本に挟まれた委譲イベントが検査範囲から丸ごと漏れるため（`validate-artifact.rb` が同じ失敗様式に対して採っている対処と同一）。

## 5. 保留の上限（未コミット滞留のリスク管理）

案 3 の成果物は「コミットされずワーキングツリーに残る `.md` と `index.jsonl` の追記」である。消費者はファイルを読むため機能上の影響は無いが、Git 履歴に残らない期間が延びるのは望ましくない。上限は 2 つ:

1. **当日内**（条件 7）: 未コミットの `.md` に当周と異なる日付のものがあれば、その周は保留せずコミットする（＝翌日の最初の周が前日分をフラッシュする）。丸 1 日 no-op でも**その日のコミットは 1 本**に収まる。
2. **次にコミットする周**: 変化のあった周は必ず保留分ごとコミットする（`git add -- <許可パス>` が未追跡ファイルを含めてステージするため、追加の手当ては不要）。

結果として、未コミットの滞留期間は「**当日 + 次の 1 周が回るまで**」に収まる。次の周がいつまでも来ない場合（拍動そのものの停止）は本機構の守備範囲ではなく、[heartbeat-detection.md](./heartbeat-detection.md) の検知が担う。

**締めジョブ（start-day 手順5）でフラッシュしない理由**: 締めジョブはサイクルロックを取らないため、run-cycle 定期便と重なると書きかけの台帳を巻き込んだ部分コミットを作りうる。上限 1・2 で滞留は十分に抑えられるため、ロック設計へ手を入れる価値が無いと判断した。

## 6. まとめコミット時の検証範囲

保留中の周の成果物は、そのまとめコミットで初めて Git 履歴へ入る。**無検証のまま履歴に入るのを防ぐ**ため、コミットする周は検算の範囲を広げる（手順6）:

| 対象 | 通常の周 | 保留分を束ねる周 |
| --- | --- | --- |
| `journal-md` | 当周の `.md` 1 件 | `noop-check.rb` の `pending_md_file=` に挙がった**未コミットの `.md` 全件** |
| `journal-index` | `--tail 1 --expect-cycle <当周>` | `--tail <pending_index_lines> --expect-cycle <当周>` |
| 1:1 対応 | （保留なし） | `pending_index_lines` と `pending_cycles`（未コミットの新規 `.md` 件数）の一致を判定側が検査。崩れていれば判定不能 |

`--tail n` は「末尾 n 件の非空レコードを検証し、n 件以上存在すること」を要求し、`--expect-cycle` は「末尾レコードが当周の行であること」を証明する。**両者は既存のバリデータのまま組み合わせられる**ため、契約物（スキーマ・バリデータ・フィクスチャ）の変更は不要だった（保留が無い周は `--tail 1`＝従来どおり）。`pending_index_lines` が得られなかった場合は `--tail 1` へフォールバックし、範囲を確保できなかった旨をサイクルレポートに記載する。

**`pending_index_lines` は「非空レコード数」で数える**（物理追加行数ではない）。`--tail n` が非空レコード基準であるため、物理行数で数えると保留区間に空行が 1 行混ざっただけで `--tail` が既コミット行まで遡り、契約導入前の不正行に当たって**まとめコミットが恒久的に失敗する**（`--tail` の範囲限定はまさにその恒久失敗を避けるために導入された機構）。実装は「現在の非空レコード数 − `HEAD` の非空レコード数」で求め、あわせて **`HEAD` の内容が現在の内容の前方一致であること**（append-only の不変条項）も検証する。
