# no-op 周の軽量化 — コミットだけを変化のあった周にまとめる（Issue [#82](https://github.com/masanami/claude-flywheel/issues/82)）

> **ステータス**: 実装済み。判定の参照実装は [`scripts/noop-check.rb`](../scripts/noop-check.rb)、呼び出し規定の正本は [run-cycle SKILL.md](../skills/run-cycle/SKILL.md) 手順6。

## 1. 背景（何が起きたか）

自走を 1 日回したところ、**5 周のうち 4 周が完全な no-op**（`touched_issues` が空）だった。前進可能な課題がすべて人間の承認ゲート（FR-13 / FR-32 / FR-22）で止まっており、エージェント側に実行できる作業が無い状態である。

no-op 自体は設計どおりの挙動で問題ではない。問題は**記録のコスト**で、変化ゼロの周でも毎回 `journal/YYYY-MM-DD-cycle.md` の生成・`journal/index.jsonl` への 1 行 append・それらの Git コミットが発生し、**Git 履歴が観測ノイズで埋まって「実際に何かが動いた周」を見つけにくくなる**（観測日 2026-08-13 に cycle-2〜cycle-5 の 4 ファイル＋4 コミットが「変化なし」の記録のために積まれた）。

**単純に「書かない」ではズレる**——`index.jsonl` の行数は複数の消費者の入力になっている（§2）。

## 2. 消費者への影響（実コードで確認した事実）

`index.jsonl` を読む消費者は 3 者。いずれも**Git のコミットではなくワーキングツリー上のファイルを読む**。

| 消費者 | 読み方（実装） | 行数・スキーマへの依存 |
| --- | --- | --- |
| `start-day` の締めジョブ（reflect しきい値判定） | [start-day SKILL.md](../skills/start-day/SKILL.md) 手順5-3: 総行数 `T` と当日分 `t` を数え `floor(T / N) > floor((T − t) / N)` | **行数に強く依存**。no-op 周の行を落とすと周回カウントがズレる |
| `reflect` | [reflect SKILL.md](../skills/reflect/SKILL.md): `pending_approvals` の頻発ゲート・`delegations` の失敗傾向を集計する追加入力 | フィールドの形に依存（行数そのものは締めジョブ側の判定に使われる） |
| claude-flywheel-board のパーサ | `src/server/parsers/journal.ts` の `parseJournal`（行ごとに JSON.parse → 全 7 フィールドを型検証。`deriveLogEntries` は `touched_issues[].id` と `pending_approvals[].issue` を課題 ID で突き合わせる） | **全 7 フィールド必須の形に依存**。ファイルパスは `watcher.ts` の `JOURNAL_FILE_NAME = journal/index.jsonl` を chokidar で監視。**`.md` は一切読まない** |

**確認できた重要な性質**:

- 3 者とも**ファイルを読む**（`git log` を読む消費者はいない）。したがって**コミットの粒度を変えても消費者の入力は 1 バイトも変わらない**。
- board のパーサは JSON オブジェクトの**追加フィールドを拒否しない**（`validateJournalEntry` は必須フィールドの型だけを見る）が、契約側のスキーマ（[`contracts/schemas/journal-index.schema.json`](../contracts/schemas/journal-index.schema.json)）は `additionalProperties: false` のため、フィールドを増やす案は**バリデータで違反**になる。
- run-cycle 手順6 の `validate-artifact.rb journal-index --tail 1 --expect-cycle <当周>` は「当周に append した 1 行が当周のもの（`date`・`seq` 一致）であること」を証明する。**毎周 1 行 append される前提**の上に立っている。

## 3. 3 案の比較

| # | 案 | スキーマ／1:1 対応 | `--tail --expect-cycle` | reflect / start-day の行数 | board | ノイズ削減 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | no-op 周は `.md` を生成せず `index.jsonl` に 1 行だけ残す | **1:1 対応が崩れる**（`journal-md` 検査と board のセクション対応の前提）。`date`/`seq` から `.md` 名を導けない行が生まれる | 維持できる | 維持できる | 直接の破綻はない（`.md` を読まないため） | **不十分**（`.md` は減るが `index.jsonl` の append とコミットは毎周残る＝**履歴のノイズは減らない**） | **不採用** |
| 2 | 連続 no-op を 1 エントリに集約（`seq` 範囲＋回数） | スキーマ変更（新フィールド）。集約のたびに**末尾行を書き換える**＝ `index.jsonl` の append-only 不変条項に違反 | **破綻**（末尾行が「当周の 1 行」でなくなる） | **破綻**（1 行＝ N 周になり、行数カウントを重み付き集計へ変更する必要） | **破綻**（`additionalProperties: false`・board の追随が必須） | 大きい | **不採用** |
| 3 | 記録は現状どおり毎周行い、**コミットだけ**を変化のあった周にまとめる | **無変更** | **無変更**（保留分を含むコミットでは `--tail` を広げるだけ。`--expect-cycle` の意味論は同じ） | **無変更** | **無変更** | 目的そのもの（履歴のノイズだけを削る） | **採用** |

**採用根拠**: 問題は「記録が多いこと」ではなく「**Git 履歴に変化ゼロのコミットが並ぶこと**」である。案 1 は問題の所在（コミット）を外しており、案 2 は 4 つの契約（スキーマ・append-only・同一性証明・行数カウント）すべてを同時に壊す。案 3 は**契約物の変更をゼロ**にしたまま目的を達成する。起票者の推奨とも一致する。

**案 3 が持ち込む唯一の新しいリスクは「未コミットの成果物がワーキングツリーに滞留すること」**で、これは §5 の 2 つの上限で抑える。

## 4. 「変化なし（no-op）」の機械的定義

判定の正本は [`scripts/noop-check.rb`](../scripts/noop-check.rb) 冒頭のコメント。**次の 7 条件がすべて成立したときだけ no-op**（1 つでも欠ければコミットする＝ fail-closed）。

| # | 条件 | 何を防ぐか |
| --- | --- | --- |
| 1 | 台帳・アーカイブ・記憶（`--path` の対象＝サイクルコミットの許可パスから journal を除いたもの）に**未コミットの差分が無い**（追跡・未追跡とも） | 「台帳を書き換えたのにコミットされない」 |
| 2 | 当周の `index.jsonl` 行の `touched_issues` / `delegations` / `pr_urls` が**すべて空** | ステータス遷移・委譲・PR 作成の取りこぼし |
| 3 | `pending_approvals` の **(gate, issue) 集合が前周の行と一致**する | 承認待ちの**新規発生・解消**（ステータス遷移を伴わない FR-22 ゲート等） |
| 4 | 当周の `.md` の ①触った課題 ②委譲 ③PR・ブランチ URL ④承認待ちゲート一覧 に **`なし` で始まらない記載が無い** | `.md` と `index.jsonl` の 1:1 の食い違い（`.md` にだけ書かれた変化） |
| 5 | 当周の `runs.jsonl` に `cycle_start` / `cycle_end` **以外のイベントが無い** | 委譲・差し込み・`delegate_end` の事後補記の取りこぼし（journal への記録漏れがあっても捕捉する裏取り） |
| 6 | `--notable` が 1 件も渡されていない | 機械で検出できない特筆事項（heartbeat 警告・periodic-audit 起動 等。列挙は手順6 が正本） |
| 7 | 未コミットの journal `.md` が**当周と同じ日付のものだけ** | 保留の無限延長（§5） |

### `decisions`（⑤判断と根拠）を判定に使わない理由

run-cycle は**変化ゼロの周でも必ず何らかの判断を書き残す**（実運用ワークスペースの 20/20 周で `decisions` が非空。初回サイクルの「ソース宣言が無いため ingest スキップ」すら記録される）。したがって `decisions` は「変化の信号」として機能せず、判定に含めると本機能は**一度も発火しない**。`decisions` に載る事象のうち「変化」に当たるものは条件 1〜6 のいずれかが捕捉し、機械で捕捉できないものは条件 6（`--notable`）が受け持つ。

### `なし` は前方一致で判定する

条件 4 は「その行が `なし` で**始まる**か」で判定する（完全一致にしない）。実運用ワークスペースの真の no-op 周（2026-08-14 seq 1・初回サイクル）は `- なし（台帳に課題エントリなし）` と理由を括弧書きで添えており、完全一致だと**本当に no-op の周でも常に「変化あり」になり本機能が発火しない**（`decisions` を判定に含めた場合と同じ失敗様式）。①〜④に書かれる実際の記録は課題 ID・repo 名・URL・ゲート名であり `なし` で始まらないため、前方一致でも取りこぼしは生じない。`特になし` のように `なし` で始まらない言い回しは（安全側に）変化として扱う。

### fail-closed の徹底

- **判定不能（exit 2）は「変化あり」と同じに扱う**（コミットする）。`runs.jsonl` 不在・`index.jsonl` の末尾行が当周でない・スキーマ違反・git 実行不能などが該当する。
- **スクリプトの起動自体の失敗（exit 126/127＝ruby 未導入）も判定不能**。ゲートが効かない環境では**従来どおりの毎周コミット**へ縮退する（[contracts/README.md](../contracts/README.md) §実行環境の前提と同じ縮退規律）。
- **保留してよいのは exit 0 のときだけ**。「実行しなかった」「読めなかった」を「変化なし」に読み替えない。
- **判定より後に判明する事象**（検算の exit 2・未終了 `*_start` の検出）は、手順6 の「保留の取り消し条件」が後段で上書きする。

## 5. 保留の上限（未コミット滞留のリスク管理）

案 3 の成果物は「コミットされずワーキングツリーに残る `.md` と `index.jsonl` の追記」である。消費者はファイルを読むため機能上の影響は無いが、Git 履歴に残らない期間が延びるのは望ましくない。上限は 2 つ:

1. **当日内**（条件 7）: 未コミットの `.md` に当周と異なる日付のものがあれば、その周は保留せずコミットする（＝翌日の最初の周が前日分をフラッシュする）。丸 1 日 no-op でも**その日のコミットは 1 本**に収まる。
2. **次にコミットする周**: 変化のあった周は必ず保留分ごとコミットする（`git add -- <許可パス>` が未追跡ファイルを含めてステージするため、追加の手当ては不要）。

結果として、未コミットの滞留期間は「**当日 + 次の 1 周が回るまで**」に収まる。次の周がいつまでも来ない場合（拍動そのものの停止）は本機構の守備範囲ではなく、[heartbeat-detection.md](./heartbeat-detection.md) の検知が担う。

**締めジョブ（start-day 手順5）でフラッシュしない理由**: 締めジョブはサイクルロックを取らないため、run-cycle 定期便と重なると書きかけの台帳を巻き込んだ部分コミットを作りうる。上限 1・2 で滞留は十分に抑えられるため、ロック設計へ手を入れる価値が無いと判断した。

## 6. まとめコミット時の検証範囲

保留中の周の成果物は、そのまとめコミットで初めて Git 履歴へ入る。**無検証のまま履歴に入るのを防ぐ**ため、コミットする周は検算の範囲を広げる（手順6）:

| 対象 | 通常の周 | 保留分を束ねる周 |
| --- | --- | --- |
| `journal-md` | 当周の `.md` 1 件 | `noop-check.rb` の `pending_md_file=` に挙がった**未コミットの `.md` 全件** |
| `journal-index` | `--tail 1 --expect-cycle <当周>` | `--tail <pending_index_lines> --expect-cycle <当周>` |

`--tail n` は「末尾 n 件の非空レコードを検証し、n 件以上存在すること」を要求し、`--expect-cycle` は「末尾レコードが当周の行であること」を証明する。**両者は既存のバリデータのまま組み合わせられる**ため、契約物（スキーマ・バリデータ・フィクスチャ）の変更は不要だった（保留が無い周は `--tail 1`＝従来どおり）。`pending_index_lines` が得られなかった場合は `--tail 1` へフォールバックし、範囲を確保できなかった旨をサイクルレポートに記載する。
