# 課題台帳フォーマット

> 各エージェントの **課題台帳（`challenge-ledger.md`）** の記入形式。人間は**共有ソース**に課題を書き、エージェントが取り込み時に「分類欄」を埋める（自分のどのポジションが引き受けるか）。
> 実体は各エージェントのリポジトリ直下の `challenge-ledger.md`。雛形は [`templates/challenge-ledger.md`](../templates/challenge-ledger.md)。共有ソースからの取り込みは [architecture.md §3.1](./architecture.md)。

## 役割分担

| 記入者 | 範囲 | ポイント |
| --- | --- | --- |
| **人間**（共有ソース） | 「人間記入欄」 | ドメインやサービスを知らなくてよい。困りごと・期待を自由に書く |
| **エージェント**（取り込み時） | 「分類欄」 | 自分の守備範囲か判断し、引き受けるポジションを割り当てる |
| **機械生成**（監査スキル） | 「人間記入欄」＋監査元マーカー | 定期監査の検出結果を起票する（§監査元マーカー）。承認ゲートは通常どおり通す |

> エージェント間の振り分けは本台帳では行わない（fleet スコープ＝人間。[architecture.md §3.2](./architecture.md)）。

## エントリ・テンプレート

```markdown
### [C-001] <タイトル>

**人間記入欄**
- 起票者 / 起票日: <name> / <YYYY-MM-DD>
- 説明: <背景・困っていること・期待する状態を自由記述>
- 完了条件（任意・分かれば）: <こうなれば完了>
- 体感の緊急度（任意）: 高 | 中 | 低

**分類欄（エージェントが記入）**
- 担当ポジション: <position 名 / 単一ポジションのエージェントでは自明>
- 関連サービス: <service-a, service-b ...>（任意）
- 優先度: P0 | P1 | P2
- ステータス: 未分類 → 分類済 → 計画承認待ち → 着手中 → 検証中 → 完了確認待ち → 完了
- タスク案: <run-cycle の計画ステップが記入。番号付きリストで複数可>
- 承認（人間がチェック）:
  - [ ] 計画を承認（FR-13）
  - [ ] 完了を承認（FR-32）
- 取り込み元: <source-id> / <外部キー>（取り込み: <YYYY-MM-DD>）<!-- fp:<フィンガープリント> -->（外部ソースから取り込んだ場合のみ・§取り込み元マーカー）
- 監査元: <ジョブid> / <対象>（監査: <YYYY-MM-DD>）<!-- audit:<ジョブid>:<対象> afp:<フィンガープリント> -->（機械生成エントリのみ・§監査元マーカー。取り込み元マーカーとは排他）
- 備考: <要相談の理由など>
```

> **記入者は 3 種類ある**: 人間（共有ソース → 人間記入欄）／エージェント（分類欄）に加え、**機械生成エントリ**（[periodic-audit](../skills/periodic-audit/SKILL.md) が監査結果から人間記入欄まで書く。§監査元マーカー）。機械生成エントリも承認ゲート（FR-13 / FR-32）は通常どおり通す。

## 分類ルール（取り込み・自ポジション割当）

1. 課題が**自分の守備範囲**（ポジションの関心範囲）に入るか判断する（記憶 `map` を参照）。
2. 入る → 引き受ける**ポジションを割当**、ステータス → 分類済（単一ポジションなら自明）。
3. 範囲外 → **取り込まない**（共有ソースに残す）。
4. 曖昧 / 他エージェントと重複しそう → **要相談**（人間へ＝承認ポイント）。エージェント間の振り分けは人間（fleet スコープ）。

## 承認プロトコル（FR-13 / FR-32 の実装）

承認は分類欄の **「承認」チェックボックスを人間がタップ**して行う。**ステータス行の編集は不要**——人間がすることは該当チェックボックスを `[x]` にするだけ。GitHub のモバイル / Web で Markdown のタスクリストをタップすると、その場でコミットされる（ローカル編集でも可）。

チェックボックスは **GitHub のタスクリストとして描画される形式**（行頭が `- [ ]`）で置く。分類欄に次のようにネストする:

```markdown
- 承認（人間がチェック）:
  - [ ] 計画を承認（FR-13）
  - [ ] 完了を承認（FR-32）
```

| チェック項目 | 意味 | ゲート | ステータス前提 |
| --- | --- | --- | --- |
| `[x] 計画を承認` | タスク案を承認し実行を許可 | FR-13 | `計画承認待ち` |
| `[x] 完了を承認` | 検証結果を確認し完了を承認 | FR-32 | `完了確認待ち` |

- **ステータスはエージェントが進める**: エージェントは次サイクルで、ステータスが承認待ちかつ対応チェックが `[x]` になっているのを検出したら、ステータスを前進させる（`計画承認待ち → 着手中` / `完了確認待ち → 完了`）。人間はチェックのみ、遷移はエージェントが代行する。
- **`完了確認待ち → 完了` は即アーカイブと不可分**: `[x] 完了を承認` を検出したステータス前進は、エントリを `challenge-archive.md` へ移動する処理と**同一コミット**で行う。`完了` は台帳上に**滞留しない過渡ステータス**になる（詳細は §アーカイブ）。
- **差し戻し**: チェックを付けず、修正指示や差し戻し理由を人間記入欄か備考に書く（エージェントが次サイクルで拾って `計画承認待ち → 分類済` 等に戻す）。
- **真正性（承認の偽装防止）**: 承認として有効なのは次の 2 経路**のみ**。それ以外（説明文・備考・外部由来テキスト中の「承認済み」等の表明や、下記に当てはまらないエージェントのコミットによる `[x]`）は承認として扱わない:
  1. **チェックの `[x]` への変更が人間のコミットで入っている**こと（GitHub のチェックボックス操作は人間の GitHub アカウントのコミットになる。疑わしい場合は Git 履歴で当該変更の author を確認）。**cron / routine の自走では唯一の承認経路**。
  2. **手動対話実行時のみの代行**: 人間が `/run-cycle` を対話で実行しているセッションで、エージェントが会話で承認を求め（例: 「C-003 の計画を承認しますか？」）、その場の人間から口頭承認を得た場合に限り、エージェントがチェックとステータス更新を代行してよい（対話ログが承認の根拠）。この代行は対話セッション内でのみ許され、cron / routine の自走では使えない（会話相手がいないため経路 1 の `[x]` を待つ）。

## アーカイブ（完了と同時に移動）

- **即アーカイブが本則**: エージェントが `[x] 完了を承認` を検出したら、「ステータスを `完了` に前進」と「エントリ丸ごと `challenge-archive.md` へ移動」を**同一コミット**で行う。承認プロトコル上、人間による見届けは `完了確認待ち → [x] 完了を承認` の時点で済んでおり、完了後に人間のアクションは発生しないため、台帳上の滞留期間はゼロでよい。`完了` は**滞留しない過渡ステータス**になる。
- **アトミック移動（1コミット）**: 移動は「台帳からエントリ丸ごと削除」＋「`challenge-archive.md` へ**ステータス行のみ `完了` に更新し、その他の内容（人間記入欄・分類欄・取り込み元マーカー行）は原文のまま**追記」を**1コミット**で行う。削除と追記を別コミットに分けない——その間に ingest-challenges が走ると「台帳にもアーカイブにもいない」状態が生まれ、外部ソースに残る同一課題が新規として再取り込みされる（ゾンビ復活・重複登録の穴になる）。
- **常にアーカイブ（削除しない）**: 外部ソース由来（取り込み元マーカーあり）でも手書き（マーカーなし）でも、完了エントリは**常にアーカイブへ移動**する（削除はしない）。取り込み元マーカーの有無で運用を分岐させない。**例外**: `github-issue` ソースの assignee ポリシー不適合による取り込み解除（着手前・未完了エントリのみが対象。§取り込み元マーカー）は、この「完了→アーカイブ」フローとは別の経路であり、削除しアーカイブへは移動しない（[ingest-challenges §4](../skills/ingest-challenges/SKILL.md) 参照）。
- **取り込み元マーカー行はアーカイブ側でも保持する**。ingest-challenges の再取り込み照合は**台帳＋アーカイブの両方**を対象にする（アーカイブ済み課題を「キー未登録＝新規」と誤認して再取り込みしないため。アーカイブ設計は冪等性と不可分）。**監査元マーカー行も同様に原文のまま保持する**（ただしこちらの再監査照合は台帳のみを対象にする。理由は §監査元マーカー）。
- **移動はエントリ境界（見出しパターン）で切り、前後で検算する**。行番号演算による移動は隣接エントリのマーカーを壊すため使わない（手順と検算コマンドは §台帳を機械で編集するときの規律）。**台帳とアーカイブの 2 ファイル更新は `mv` 2 回では原子的にならない**ため、同節「2 ファイル更新のトランザクション」のマーカー＋起動時復旧に従う（1 コミットに収める規律は、中断からの回収とは別の話であり両方必要）。
- **閾値ルールはバックストップ（正常系では発火しない）**: 即アーカイブが機能していれば台帳に `完了` エントリは滞留しない。手動編集などで `完了` エントリが台帳に残ってしまった場合の掃除規定として、「完了から 30 日経過、または完了エントリが 20 件超」を閾値に、次サイクルの整理（run-cycle 手順1）でエントリごと `challenge-archive.md` へ移す。「完了から 30 日」の**基準日は、当該エントリのステータス行が `完了` になったコミットの日時**とする（`git log` で該当行の変更を遡って特定）。台帳テンプレートへの完了日時フィールドの追加は行わない（バックストップは異常系の低頻度な掃除規定であり、正常系の台帳フォーマットを太らせない）。基準日の特定が煩雑な場合は、日数基準の判定を待たず**件数基準（完了エントリが 20 件超）のみでも発火**してよい。このときも上記アトミック移動・マーカー保持・常にアーカイブの各方針に従う。
- **将来の年次分割方針**: アーカイブが肥大した場合（目安: 数千行超）は、タスク別分割ではなく**年次分割**（`challenge-archive-2026.md` 等）とする。分割時は ingest-challenges の照合対象を `challenge-archive*.md` の glob に広げる。当面（数千行に達するまで）は 1 ファイル運用を維持する。

## 取り込み元マーカー（ingestion の冪等性）

外部ソースから取り込んだ課題（[ingest-challenges](../skills/ingest-challenges/SKILL.md)）は、分類欄に**取り込み元マーカー**を 1 行持つ。これで**同じ課題の再取り込みを冪等**にする（二重登録しない）。

```markdown
- 取り込み元: <source-id> / <外部キー>（取り込み: <YYYY-MM-DD>）<!-- fp:<フィンガープリント> -->
```

- **`<source-id>`**: 取り込み元（`challenge-sources.md` の `id`）。
- **`<外部キー>`**: ソース側の**安定 ID**（Notion page id / Slack ts / 見出し ID 等）。再取り込みの照合キー。
- **`fp:<フィンガープリント>`**: **人間記入欄**（説明・完了条件・緊急度）を正規化した指紋。人間は読まないので HTML コメントに隠す。
- 再取り込み時の判定（詳細は ingest-challenges §4）:
  - キー未登録 → **新規追記**（ステータス 未分類）。
  - キー既登録・`fp` 一致 → **スキップ**（変化なし）。
  - キー既登録・`fp` 不一致 → **人間記入欄のみ更新**し `fp`・取り込み日を更新。**分類欄の他項目（担当ポジション・関連サービス・優先度・ステータス・タスク案・備考）はすべて保持**（内部正本の分類・進行を壊さない）。
- **マーカー無しの手書きエントリは ingestion の対象外**（触らない）。手書き運用と取り込み運用は共存できる。
- **ポリシー不適合エントリの取り込み解除**（`github-issue` ソースのみ）: マーカー一致で台帳に「キー既登録」のエントリについて、最新の `assignees` が現在の `assignee_policy` / `self_assignees` に合致しなくなった場合（他人が新たに assign された・`self-only` で unassigned になった等）、**人間承認前・実作業が未着手**（未分類／分類済／計画承認待ち〔未承認〕）のエントリはアーカイブへ移動せず**台帳から丸ごと削除**する（マーカーごと消える。アーカイブに残すと assign 解除後の再取り込みが「既登録」と誤判定されるため）。**着手中以降（承認済み含む）**のエントリは自動削除せず、ingest-challenges のレポートへ「要対応」として残す（台帳・分類欄は変更しない）。アーカイブ側でマーカーが一致した場合はこの判定の対象外（アーカイブは完了フローの正本のため変更しない）。詳細・判定基準は [ingest-challenges §4](../skills/ingest-challenges/SKILL.md) 参照。

## 監査元マーカー（機械生成エントリの冪等性）

[periodic-audit](../skills/periodic-audit/SKILL.md) が監査結果から起票したエントリは、分類欄に**監査元マーカー**を 1 行持つ。これで**同じ（監査ジョブ×対象）の再監査を冪等**にする。

```markdown
- 監査元: <ジョブid> / <repo名>（監査: <YYYY-MM-DD>）<!-- audit:<ジョブid>:<repo名> afp:<フィンガープリント> -->
```

- **`<ジョブid>:<対象>`**（HTML コメント内の `audit:` 以降）: 再監査の照合キー。`<ジョブid>` は `.flywheel/cadence.json` の `audit.jobs[].id`（**運用者が宣言する識別子**であり、flywheel はその意味を解釈しない不透明な文字列）。**書式は `^[A-Za-z0-9._-]{1,64}$` に固定**する（`:` はキーの区切りを壊し、改行・制御文字・`-->` は**マーカーそのものの境界を壊す**。エスケープではなく許可文字リストで弾く＝検証規則の正本は [periodic-audit](../skills/periodic-audit/SKILL.md) §ジョブ宣言の検証で、start-day 手順1・run-cycle 手順0 も同じ規則を適用する）。**同じ repo に複数の監査ジョブを宣言していれば、ジョブごとに別エントリ**になる。
- **同定キー・永続識別子は接続ツール中立・方法論中立に保つ**。監査元マーカー（可視部・HTML コメント部の両方）が持つのは**運用者が宣言したジョブ `id`** だけとし、**起票者の表記**は `定期監査（機械生成）` のように機構の名前に留める。接続ツール名・監査スキル名・特定方法論の語彙を入れない。理由: 台帳は接続ツールより寿命が長い永続データであり、ツールを差し替えても**同じ（ジョブ×対象）の再監査が同一エントリへ突き合わされる**必要があるため（ツール名が同定キーに入ると、差し替え時に別エントリとして二重起票される）。**「どのツールのどのスキルで監査したか」は説明欄など可変部分に書く**。
- **`afp:<フィンガープリント>`**: 検出内容の指紋。`fp:`（取り込み元マーカー）と**別ラベル**にして、ingestion の照合ロジックと衝突させない。算式は取り込み元マーカーと同じ（`printf '%s' "<正規化文字列>" | shasum -a 256 | cut -c1-12`）だが、**指紋の対象は検出集合であり、日付やコミット SHA は含めない**（対象にコミットが入るたびに「更新あり」となって台帳が無駄に書き換わるのを防ぐ）。
- **取り込み元マーカーとは排他**（同一エントリに両方は置かない）。これにより ingest-challenges の「マーカー無しの手書きエントリは触らない」規約がそのまま効き、機械生成エントリが ingestion の**新規判定・`fp` 更新・ポリシー不適合による取り込み解除（削除）**の対象にならない。
- **粒度は「（監査ジョブ×対象）1 つにつき 1 エントリ」**（対象 repo が同じでもジョブが違えば別エントリ）。検出項目（finding）ごとには起票しない。テスト参照のような不安定なキーで起票すると監査のたびに現れたり消えたりするエントリが溜まり、また項目単位に分解すると「一部しか検査できていない（下限）」「未解析」という情報が失われるため。
- **照合範囲は台帳のみ。`challenge-archive*.md` は照合しない**（取り込み元マーカーとは意図的に逆）。監査が検出する状態（ドリフト等）は**再発しうる**ため、過去に解消してアーカイブ済みのものが再検出された場合は**新規課題として起票するのが正しい**。取り込み元マーカーがアーカイブを照合するのは「同一の外部 Issue の再取り込み防止」であり目的が異なる。
- 再監査時の判定（詳細は [periodic-audit](../skills/periodic-audit/SKILL.md) §5.3）:
  - キー未登録・要対応あり → **新規追記**（ステータス 未分類）。要対応なし（クリーン）なら**起票しない**。
  - キー既登録・**人間承認前**（未分類／分類済／計画承認待ち〔未チェック〕）→ `afp` 一致で**スキップ**、不一致で**説明のみ更新**し監査日・`afp` を更新。分類欄と他の人間記入欄は保持。
  - キー既登録・**着手中以降（承認済み含む）** → **台帳を変更しない**（実作業が進行中の対象を監査が書き換えると委譲先の前提が途中で変わるため）。最新結果は報告と journal にのみ残す。
- **未解析を検出結果にしない**: 監査自体が実行できなかった場合は「問題なし」と扱わず、**起票もしない**（未解析を台帳に固定すると誤った作業を誘発する）。報告にのみ「監査不能」として残す。
- **ステータスの前進・完了判定は監査スキルが代行しない**。再監査でクリーンになっても `完了` へは進めず、報告で「完了承認の候補」として示すに留める（承認プロトコル §承認の真正性 / FR-32 に従う）。
- アーカイブ時は取り込み元マーカーと同様、**監査元マーカー行も原文のまま保持**する（§アーカイブ）。

## 台帳を機械で編集するときの規律（マーカー保全）

取り込み元マーカー・監査元マーカーは**冪等性の要**であり、壊れると二重取り込み・復元不能を静かに引き起こす。実運用で、エントリ移動を**行番号演算**で行った結果、隣接エントリのマーカーを巻き込んで壊した事例がある（2026-08-17 に検出・修復）。エージェントが台帳を編集する手順（ingestion の追記・更新、監査エントリの起票、§アーカイブのアトミック移動、取り込み解除の削除）は、次を必ず守る。

> **この規律自体が新たな事故を生まないこと**: 失敗時の復旧に `git checkout -- challenge-ledger.md` のような**ファイル全体を戻す操作を使ってはならない**。台帳には人間が直接書き込む欄（人間記入欄・承認チェック）があり、機械編集より前から**未コミットの人間の変更が同居しうる**。ファイル全体を戻すとそれを巻き添えで破棄する。**元ファイルを一度も書き換えない（一時ファイル方式）ことで、そもそも復旧操作を不要にする**。

1. **エントリ境界は見出しパターンで切る**。`^### \[` にマッチする行を境界とし、**行番号のオフセット計算でエントリを移動・削除しない**。
2. **編集は一時ファイルに対して行う**。`challenge-ledger.md`（およびアーカイブ）を直接書き換えず、同じディレクトリに一時ファイル（例: `challenge-ledger.md.tmp`）を作り、そこに編集後の全文を書く。元ファイルはこの時点では無傷のまま。
3. **一時ファイルに対して検算する**。各エントリのマーカーが（取り込み元・監査元あわせて）高々 1 つであること、エントリ総数が期待値と一致することを確認する:

   ```bash
   awk '
     /^```/ { fence = !fence; next }
     fence { next }
     /^### \[/ { if (h != "") check(); h = $0; t = 0; a = 0; n++ }
     /^- 取り込み元: *[^ ]/ { t++ }
     /^- 監査元: *[^ ]/ { a++ }
     END { if (h != "") check(); printf "entries=%d ng=%d\n", n, ng }
     function check() { if (t > 1 || a > 1 || (t > 0 && a > 0)) { ng++; print "NG: " h } }
   ' challenge-ledger.md.tmp
   ```

   期待値は `ng=0` かつ `entries` が「編集前の値 ± 意図した増減」と一致すること。**編集前の値は同じコマンドを元ファイルに対して実行して実測する**（比較の基準を思い込みで置かない）。

4. **検算に成功した一時ファイルだけを元ファイルへ置換する**（`mv challenge-ledger.md.tmp challenge-ledger.md`）。同一ディレクトリ内の `mv` は原子的に置き換わるため、中途半端な内容が見える瞬間が無い。
5. **検算に失敗したら一時ファイルを捨てるだけ**にする（`rm challenge-ledger.md.tmp`）。元ファイルは一度も書き換えていないので**復旧操作は不要**であり、**`git checkout` 等でファイル全体を戻してはならない**（人間の未コミット変更を破棄するため）。検算結果を添えて報告し、コミットはしない。
6. **アーカイブへの移動を伴う操作では、移動元（台帳）と移動先（`challenge-archive.md`）の双方を一時ファイルで作り、双方の検算に成功してから双方を置換する**。ただし **`mv` が原子的なのは 1 ファイル単位であり、2 回の `mv` は原子的ではない**。途中で停止すると片方だけ適用された状態が残るため、下記「2 ファイル更新のトランザクション」に従う。

### 2 ファイル更新のトランザクション（アーカイブ移動・**復旧可能にする**）

2 回の `mv` の間でプロセスが停止すると、「台帳から消えたのにアーカイブに無い」（**消失**）か「両方にある」（**重複**）が残る。次回実行がその状態を読むと、重複登録または課題の欠落が起きる。一時ファイル方式は人間の未コミット変更を守るが、**2 ファイル間の整合は守らない**。そこで**トランザクションマーカー＋起動時復旧**を課す:

1. **マーカーを書く**（置換の前）。`.flywheel/ledger-tx.json` に、これから行う移動を記録する（`.flywheel/` はローカル・gitignore 対象）:

   ```json
   {"op":"archive","entries":["C-012"],"ledger_tmp":"challenge-ledger.md.tmp","archive_tmp":"challenge-archive.md.tmp","started_at":"<ISO8601>"}
   ```

2. **追記側を先に置換する**（`mv challenge-archive.md.tmp challenge-archive.md` → `mv challenge-ledger.md.tmp challenge-ledger.md`）。**順序は必須**: この順なら途中停止で残るのは「両方に存在」＝**重複**であり、検出も回収も可能。逆順だと「どちらにも無い」＝**消失**になり、一時ファイルが失われていれば回復できない。
3. **両方の `mv` が終わったらマーカーを削除**する。コミットは**マーカー削除後**に行う（Git 上は削除と追記で 1 コミット）。

**起動時復旧（台帳を触るすべての手順の冒頭で実施・fail-closed）**: `.flywheel/ledger-tx.json` が存在したら、**新しい編集を始める前に**前回の中断を回収する。マーカーの `entries` の各 ID について、台帳とアーカイブの実状態を見て次のとおり判定する:

| 台帳 | アーカイブ | 状態 | 復旧 |
| --- | --- | --- | --- |
| あり | あり | 手順 2 の 1 回目だけ適用（**重複**） | 台帳側から当該エントリを削除して移動を完了させる（アーカイブが正）。同節 1〜5 の一時ファイル方式で行う |
| なし | あり | 移動は**完了済み**（マーカー削除の前に停止） | マーカーを削除するだけ |
| あり | なし | 移動は**未適用** | マーカーを削除し、通常フロー（次回の完了承認検出）に委ねる |
| なし | なし | **消失**（想定外） | **台帳の編集を一切行わず停止**し、人間へ報告する。マーカーの内容・当該 ID・直前のコミットを添える（データ消失の可能性があり、機械が推測で復元しない） |

- **マーカーが残っている間は新しい台帳編集を開始しない**（回収してから進む）。回収できない行（上表の最終行）を検出した場合も同様に停止する。
- 復旧の実施有無と結果は報告に含める（黙って直さない）。

## 優先度判定の基準（外出し先）

分類欄の `優先度: P0 | P1 | P2` 欄自体のフォーマットは変更しない。**判定基準・着手順の選択基準**は各エージェントの `priority-policy.md`（雛形 [`templates/priority-policy.md`](../templates/priority-policy.md)）に外出しする。`run-cycle` 手順1・手順2 がこれを参照する（不在時は現状どおりエージェント裁量）。詳細は [`skills/run-cycle/SKILL.md`](../skills/run-cycle/SKILL.md) を参照。

## 運用メモ

- 人間は**共有ソース**に書き、各エージェントが自分に関係する分だけ取り込む。共有ソースの実体は差し替え可能で、外部ドキュメント（Notion/Doc/Slack 等）化は [ingest-challenges](../skills/ingest-challenges/SKILL.md) が担う（[requirements.md OQ-01](./requirements.md) / architecture AO-06）。取り込み元の宣言は `challenge-sources.md`（雛形 [`templates/challenge-sources.md`](../templates/challenge-sources.md)）。
- 「分類欄」はエージェントが更新するため、人間がするのは「人間記入欄」の記述と**承認チェック**（§承認プロトコルの `[x]` タップ）だけでよい。
- ステータスや担当の更新履歴は Git の差分で追える。
