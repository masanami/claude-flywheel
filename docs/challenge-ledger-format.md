# 課題台帳フォーマット

> 各エージェントの **課題台帳（`challenge-ledger.md`）** の記入形式。人間は**共有ソース**に課題を書き、エージェントが取り込み時に「分類欄」を埋める（自分のどのポジションが引き受けるか）。
> 実体は各エージェントのリポジトリ直下の `challenge-ledger.md`。雛形は [`templates/challenge-ledger.md`](../templates/challenge-ledger.md)。共有ソースからの取り込みは [architecture.md §3.1](./architecture.md)。

## 役割分担

| 記入者 | 範囲 | ポイント |
| --- | --- | --- |
| **人間**（共有ソース） | 「人間記入欄」 | ドメインやサービスを知らなくてよい。困りごと・期待を自由に書く |
| **エージェント**（取り込み時） | 「分類欄」 | 自分の守備範囲か判断し、引き受けるポジションを割り当てる |

> エージェント間の振り分けは本台帳では行わない（fleet スコープ＝人間。[architecture.md §3.2](./architecture.md)）。

## エントリ・テンプレート

```markdown
### [C-001] <タイトル>

**人間記入欄**
- 起票者 / 起票日: <name> / <YYYY-MM-DD>
- 説明: <背景・困っていること・期待する状態を自由記述>
- 完了条件（任意）: <こうなれば完了。複数あるときの書き方は §複数行フィールドの記入形式（移行フェーズに従う）>
- 体感の緊急度（任意）: 高 | 中 | 低

**分類欄（エージェントが記入）**
- 担当ポジション: <position 名 / 単一ポジションのエージェントでは自明>
- 関連サービス: <service-a, service-b ...>（任意）
- 関連リポジトリ: <owner/repo, owner/repo2 ...>（任意・複数可。§関連リポジトリ・関連Issue・関連PR）
- 関連Issue: <owner/repo#12, repo2#34 ...>（任意・複数可）
- 関連PR: <owner/repo#56, repo2#78 ...>（任意・複数可）
- 優先度: P0 | P1 | P2
- ステータス: 未分類 → 分類済 → 計画承認待ち → 着手中 → 検証中 → 完了確認待ち → 完了
- 人間への問い: <保留に入ったときだけ・エージェントが記入。§保留プロトコル>
- 人間の回答: <保留に入ったときだけ・**人間が記入**。空なら未回答。§保留プロトコル>
- タスク案:
  1. <run-cycle の計画ステップが記入。1 タスク 1 行の番号付きリスト。§複数行フィールドの記入形式>
  2. <タスク2 ...>
- 承認（人間がチェック）:
  - [ ] 計画を承認（FR-13・承認対象＝タスク案）
  - [ ] 完了を承認（FR-32）
- 取り込み元: <source-id> / <外部キー>（取り込み: <YYYY-MM-DD>）<!-- fp:<フィンガープリント> -->（外部ソースから取り込んだ場合のみ・§取り込み元マーカー）
- 備考: <要相談の理由など>
```

> **ステータスの語彙は閉じている**。上のステータス行に並ぶ `未分類 → … → 完了` は**主経路**（順に進む 7 状態）であり、これに加えて**主経路の途中から出入りする側道の状態**がある——現在は **`人間対応待ち`**（§保留プロトコル）の 1 つ。側道は直列の遷移列に並べない（並べると「必須の中間ステップ」という嘘になる）。**語彙の正本は [`contracts/ledger-status-vocabulary.tsv`](../contracts/ledger-status-vocabulary.tsv)**（`status` / `track`＝`main` \| `side` / `order`）であり、本節の連鎖はその `track=main` の記入例。両者の一致（順序込み）はテストが固定する。

> **記入者は 2 種類ある**: 人間（共有ソース → 人間記入欄）とエージェント（分類欄）。外部ソースからの取り込み（[ingest-challenges](../skills/ingest-challenges/SKILL.md)）は人間記入欄を機械が転記するが、承認ゲート（FR-13 / FR-32）は通常どおり通す。

## 複数行フィールドの記入形式（タスク案・完了条件）

**タスク案・完了条件は「フィールド行＋直下のネスト箇条書き」（複数行形式）を正規形**とする。1 行に詰め込むと「計画」として読めず、承認者（FR-13）が何を承認するのか判断できないため。

```markdown
- 完了条件（任意）:
  - <条件1>
  - <条件2>
- タスク案:
  1. <タスク1>
  2. <タスク2>
```

- **フィールド行の値は空**にし、**直下に半角スペース 2 個でインデント**した箇条書きを続ける（承認チェックボックスのネストと同じインデント幅）。
- **タスク案は番号付き**（`1.` `2.` …＝順序と参照可能性のため）、**完了条件は中黒**（`- `）を既定とする（完了条件も番号付きにしてよい）。
- **1 項目 1 行**。項目の中で改行したい場合は、さらに深いインデント（スペース 4 個）の子項目にする。
- **途中に空行を入れない**（GitHub でリストが分断され、消費側の「フィールド直下の連続ブロック」収集も切れる）。
- 値もネスト項目も無い状態（`- タスク案:` のみ）は**未記入**を意味する（計画前のエントリでは正規）。

### 移行フェーズ（順序制約・**書き手はまだ形 A で書かない**）

**「正規形の定義」と「書き手がいつ切り替えるか」は別**。複数行形式（形 A）は本節で正規形として定義するが、**書き手（[run-cycle](../skills/run-cycle/SKILL.md) 手順2・[ingest-challenges](../skills/ingest-challenges/SKILL.md) 手順3）が形 A で書き始めるのは、消費者（board）の追随が完了してから**とする。

順序を守らないと、**生成側だけが新形式になり消費者が値を落とす**——board の現行パーサはインデント行を捨てるため、形 A で書いたタスク案・完了条件はカード詳細で `-`（欠落）表示になる。それは本規定が解こうとした症状（Issue [#87](https://github.com/masanami/claude-flywheel/issues/87) の Emma・Rupert の欠落表示）を、追随済みだったワークスペースへ**拡大する**ことになる。

| フェーズ | 書き手が書く形 | 期間 |
| --- | --- | --- |
| **フェーズ 1（現在）** | **形 B（1 行）** を既定とし、1 行に収まらない場合は **形 D**（1 行要約をフィールド行に置き、詳細を直下のネスト項目に書く）。形 D なら現行 board でも 1 行要約が表示され、**情報は台帳側に残る**（1 行に潰して原意を失わせない） | board が複数行を読めない間 |
| **フェーズ 2** | **形 A（複数行）** | 下記の切り替え条件を満たしてから |

**切り替え条件（すべて満たすこと）**:

1. board 側の複数行対応（[claude-flywheel-board#151](https://github.com/masanami/claude-flywheel-board/issues/151)）がマージされている。
2. board のパーサが本リポジトリの正例フィクスチャ `contracts/fixtures/ledger/valid/multiline-and-refs.md` の **C-101（形 A）から `taskPlan` と `completionCriteria` の値を取得できる**（board 側の受理方向テストで固定されている）。判定は board リポジトリで次を実行して確認する（値が `undefined`・空でないこと）:

   ```bash
   node -e 'import("./src/server/parsers/ledger.ts").then(m=>{const r=m.parseLedgerFile(process.argv[1]).challenges.find(c=>c.id==="C-101");console.log(r.taskPlan,"|",r.completionCriteria)})' <本リポジトリ>/contracts/fixtures/ledger/valid/multiline-and-refs.md
   ```

3. 1・2 を確認したうえで、**本リポジトリの記入指示（run-cycle 手順2・ingest-challenges 手順3）を形 A へ書き換える PR** を出す。**フェーズの切り替えは本リポジトリの明示的な変更**であり、実行時に自動で切り替わるものではない（消費者の状態を書き手が実行時に判定する仕組みは持たない）。

**受理（バリデータ）は最初から形 A・B・C・D のすべてを通す**。フェーズはあくまで**書き手の記入指示**の話であり、検査を段階的に厳しくするものではない（フェーズ 2 へ移っても形 B の既存エントリは受理され続ける）。

### 受理される形・違反になる形（生成側の状態空間）

台帳を書くのは人間・run-cycle・ingest-challenges の 3 者であり、実際に 3 エージェントで 3 通りの形に分岐した実績がある（Issue [#87](https://github.com/masanami/claude-flywheel/issues/87)）。**どの形が受理され、どの形が違反かを列挙して固定する**（検査の実装は [`scripts/validate-artifact.rb`](../scripts/validate-artifact.rb)・契約は [`contracts/README.md`](../contracts/README.md)）。

| # | 形 | 例 | 判定 | **規定上**の値（消費者が実装すべき読み取り結果） |
| --- | --- | --- | --- | --- |
| A | **複数行**（フィールド行の値は空＋直下に 2 スペースのネスト箇条書き） | `- タスク案:` ＋ `  1. …` | **正規形**（新規記入はこれ） | ネスト項目の並び |
| B | **1 行**（フィールド行に値を書く） | `- タスク案: (1) … (2) …` | **受理**（後方互換。新規記入では使わない） | フィールド行の値 |
| C | **空** | `- タスク案:` のみ | **受理**（未記入＝計画前） | 空 |
| D | 1 行値＋ネスト項目の併記 | `- タスク案: 概要` ＋ `  1. …` | **受理**（非推奨。使うなら値は見出し的な 1 行に留める） | 値とネスト項目の連結 |
| E | フィールド行を持たない独自形式 | `**タスク案（承認済み）**` ＋ 箇条書き | **違反**（必須フィールド行の欠落として検出） | 欠落（board では `-` 表示） |
| F | ネスト項目のインデント欠落 | `- タスク案:` ＋ 行頭の `1. …` | **違反**（分類欄のインデントなし番号付きリストとして検出） | 欠落（フィールドとの結びつきが切れる） |

- **B（1 行形式）は既存台帳の互換のために受理し続ける**。既存エントリを一括で複数行形式へ書き換えることは求めない（既存ワークスペースの移行は [#88](https://github.com/masanami/claude-flywheel/issues/88) の flywheel-init 再実行マイグレーションの対象＝§既存ワークスペースの移行）。
- E・F は「書けたが消費者にとって壊れている」型であり、**書き込み側の検算（run-cycle 手順6）で止める**。
- **最右列は「規定上こう読むべき」であって「現行の消費者がこう読む」ではない**。現行 board は形 A・D のネスト項目を落とす（§移行フェーズ）。差が解消するまで書き手はフェーズ 1 の形で書く。
- **機械検査の範囲は分類欄のみ**: 形 F（結合切れ）の検出は**エージェントが書く分類欄**に限る。**人間記入欄は人間の自由記述と外部本文の転記（ブロック引用）が入るため機械検査の対象外**とし、行頭の箇条書きを違反にしない。したがって**人間記入欄にある `完了条件` の書き方は規定としては本節に従うが、違反しても検算は止めない**（規定と検査の範囲の差をここで明示しておく＝「検査があるから守られている」と読み替えない）。
- **F は「修復」対象であり、B の「書き換え不要」とは別物**: 形 B（1 行形式）の既存エントリは**書き換えを求めない**（内容の書き直しになるため）。一方 形 F はインデントを 2 個入れるだけの**機械的・内容保存の修復**であり、台帳（現在状態のファイル・修復が正規の運用）では検算が指摘した箇所をその場で直して進む（run-cycle 手順6 の fail-closed の通常フロー）。**アーカイブ（原文保存の履歴）では形 F を検査しない**（`archive` タイプでは結合切れ・参照フィールドの値の形の 2 検査を行わない）——アーカイブは「ステータス行以外は原文のまま」保存する規定であり、移動時に修復を強いると原文保存と衝突するため（**#88 の移行前でも、形 F のレガシーエントリをそのままアーカイブへ移せる**）。新しく壊れた形が入り込む経路は、台帳側の全体検証が塞ぐ（アーカイブへは台帳から移すため）。

### 消費側（board 等）の読み取り規則

観測プレーン（例: [claude-flywheel-board](https://github.com/masanami/claude-flywheel-board)）は次の規則で値を取る。**この節が消費側実装の参照先**（契約物のコピー元は `contracts/`）:

1. 分類欄・人間記入欄のフィールド行は**行頭（インデントなし）の `- <ラベル>: <値>`**。
2. フィールドの値は、**フィールド行の値＋直下に連続する継続行**を結合したもの。**継続行は 2 種類**あり、どちらも値に含める:
   - **インデント行**（スペース 1 個以上で始まる行）＝複数行形式のネスト項目（形 A・D）
   - **引用行**（行頭が `>`）＝ ingest-challenges が外部 Issue 本文を転記する形（`- 説明:（原文引用）` の直下に続くブロック引用。**実運用の説明欄の主要形**）
3. 値の終端は、**空行・上記いずれの継続行でもない行・次のエントリ見出し**のいずれかに達したところ。
4. 承認チェックボックス（`  - [ ] …` / `  - [x] …`）はインデント行だが**フィールド値ではない**（`- 承認（人間がチェック）:` の直下の専用構造）。
5. フェンス（コードブロック）内・HTML コメント内は台帳データではない（記入例・説明用のサンプル）。

> **引用行を値に含めるのは受理方向の要件**（規定が実運用の正規形を拒まないため）。ingest-challenges が書く説明はフィールド行の値が定型の `（原文引用）` だけで、**本文は直下のブロック引用にある**。引用行を値の外に出すと、消費者は説明を定型文字列としてしか読めず、[fp（更新検知）](#取り込み元マーカーingestion-の冪等性)も本文の変化に反応しなくなる（算出規則の正本は [ingest-challenges §4](../skills/ingest-challenges/SKILL.md)）。

## 関連リポジトリ・関連Issue・関連PR

課題から**成果物（PR）・関連 Issue・対象リポジトリ**を直接辿れるように、分類欄に 3 つの参照フィールドを持つ（Issue [#89](https://github.com/masanami/claude-flywheel/issues/89)）。**いずれも任意・複数可**。

```markdown
- 関連リポジトリ: masanami/claude-flywheel, masanami/claude-flywheel-board
- 関連Issue: claude-flywheel#87, claude-flywheel#89
- 関連PR: claude-flywheel#93
```

| フィールド | 値の形式 | 意味 |
| --- | --- | --- |
| `関連リポジトリ` | `<owner>/<repo>` のカンマ区切り | **作業対象**のリポジトリ。**`repos.tsv` の `<name>` 列をそのまま書かない**（`<name>` は owner を含まないローカルの短縮名）。owner は同じ行の `<url>` 列から取る（下記） |
| `関連Issue` | `<owner>/<repo>#<number>` のカンマ区切り（`<repo>#<number>` の短縮形も可） | 課題に関係する Issue（取り込み元の Issue・作業中に起票した Issue） |
| `関連PR` | 同上 | 課題の成果物となる PR |

- **`関連サービス` とは併存**（統合しない）。`関連サービス` はドメイン上のサービス名（人間・ポジションの語彙）、`関連リポジトリ` は `<owner>/<repo>` の実リポジトリ。1 サービスが複数リポジトリに分かれることも、1 リポジトリが複数サービスを含むこともあるため、対応は 1:1 に固定しない。
- **`repos.tsv` からの導き方（書き手向け・記入時の唯一の手順）**: `repos.tsv` の行は `<name>  <url>  <branch>` で、**`<name>` 列には owner が無い**（例: `claude-flywheel`）。`関連リポジトリ` には**`<url>` の `github.com/` 以降**（例: `https://github.com/masanami/claude-flywheel` → `masanami/claude-flywheel`）を書く。`<name>` をそのまま書くとバリデータが違反として弾き、run-cycle 手順6 の fail-closed でコミットが止まる。

  ```bash
  # repos.tsv の <name> から <owner>/<repo> を導く（コメント行・空行を除外）
  awk -v n="<name>" '$0 !~ /^[ \t]*#/ && NF >= 2 && $1 == n { sub(/.*github\.com[:\/]/, "", $2); sub(/\.git$/, "", $2); print $2 }' repos.tsv
  ```
- **短縮形（`<repo>#<number>`）の owner 解決は消費側**が行う。解決手順は **同エントリの `関連リポジトリ` に同名 `<repo>` があればその owner を使う**、無ければ **owner 不明としてリンク化せずテキストのまま表示する**（消費者がワークスペースの `repos.tsv` を読める前提は置かない＝観測プレーンが持たない情報に依存させない）。書き手は迷ったら `<owner>/<repo>#<number>` の完全形で書く。
- **追記のみ・重複させない**（既存の値を消さない）。**クローズ済みの Issue・PR も残す**（履歴として有用）。マージされなかった PR も削除しない。
- **空欄＝該当なし**。`（未作成）` のようなプレースホルダ文字列は書かない（消費側がリンク化できず、機械判定も壊れる）。
- **リンク化は消費側（board 等）の責務**。台帳には URL ではなく `<repo>#<number>` の短い参照を書く（URL を書くと行が長くなり、GitHub 上の可読性が落ちる）。
- **後方互換**: これらの行が無いエントリはそのまま有効（消費側は空として扱う）。バリデータも**必須にしない**。既存ワークスペースへの行追加は [#88](https://github.com/masanami/claude-flywheel/issues/88) の対象（§既存ワークスペースの移行。**台帳のみ**追加し、原文保存のアーカイブには追加しない）。

### 記入責務

| フィールド | 記入者 | タイミング |
| --- | --- | --- |
| `関連リポジトリ` | run-cycle 手順2（計画） | タスク案を書くときに作業対象が確定する。手順3で対象が増えたら追記する |
| `関連Issue` | ingest-challenges 手順4（新規追記時・`github-issue` ソースのみ） / run-cycle 手順3 | 取り込み時にソース Issue を記載。作業中に起票した Issue は手順3で追記する |
| `関連PR` | run-cycle 手順3（PR 作成の直後） | PR URL をサイクルレポート・journal に出す既存義務に、台帳への追記を加える |

- `関連Issue` と**取り込み元マーカーは役割が別**（マーカーは ingestion の冪等性キー＝機械用・HTML コメント込み、`関連Issue` は人間と観測プレーンが辿るための可読な参照）。値が重複しても構わない。
- 対象リポジトリが記入されていると、**承認者は FR-13 の承認時点で「どのリポジトリが触られるか」も判断材料にできる**（§FR-13 の承認対象）。

## 分類ルール（取り込み・自ポジション割当）

1. 課題が**自分の守備範囲**（ポジションの関心範囲）に入るか判断する（記憶 `map` を参照）。
2. 入る → 引き受ける**ポジションを割当**、ステータス → 分類済（単一ポジションなら自明）。
3. 範囲外 → **取り込まない**（共有ソースに残す）。
4. 曖昧 / 他エージェントと重複しそう → **要相談**（人間へ＝承認ポイント）。エージェント間の振り分けは人間（fleet スコープ）。

## 承認プロトコル（FR-13 / FR-32 の実装）

承認は分類欄の **「承認」チェックボックスを人間がタップ**して行う。**ステータス行の編集は不要**——人間がすることは該当チェックボックスを `[x]` にするだけ。GitHub のモバイル / Web で Markdown のタスクリストをタップすると、その場でコミットされる（ローカル編集でも可）。

チェックボックスは **GitHub のタスクリストとして描画される形式**（行頭が `- [ ]`）で置く。分類欄に次のようにネストする:

```markdown
- 承認（人間がチェック）:
  - [ ] 計画を承認（FR-13・承認対象＝タスク案）
  - [ ] 完了を承認（FR-32）
```

| チェック項目 | 意味 | ゲート | ステータス前提 |
| --- | --- | --- | --- |
| `[x] 計画を承認` | **タスク案**（＝タスク分解・方向性）を承認し実行を許可（§FR-13 の承認対象） | FR-13 | `計画承認待ち` |
| `[x] 完了を承認` | 検証結果を確認し完了を承認 | FR-32 | `完了確認待ち` |

**チェック行のラベルは承認対象を自分で名乗る**（`計画を承認（FR-13・承認対象＝タスク案）`）。台帳を直接読む人も、台帳をレンダリングする観測プレーンを見る人も、**照会なしに「何を承認しているか」を判断できる**ようにするため。ラベル後半（`（…）` 部分）は表示上の注記であり、**承認の検出はラベルの前方一致**で行う——対象は分類欄の `- 承認（人間がチェック）:` の直下にネストされた**2 スペースインデントのチェックボックス行**（`  - [ ] 計画を承認…` / `  - [x] 計画を承認…`）で、**`計画を承認` / `完了を承認` までの前方一致**が同定に使う部分、**承認の成立はチェック状態が `[x]` であること**（`[ ]` は未承認）。したがって旧表記 `計画を承認（FR-13）` のままのエントリも有効。

- **ステータスはエージェントが進める**: エージェントは次サイクルで、ステータスが承認待ちかつ対応チェックが `[x]` になっているのを検出したら、ステータスを前進させる（`計画承認待ち → 着手中` / `完了確認待ち → 完了`）。人間はチェックのみ、遷移はエージェントが代行する。
- **`完了確認待ち → 完了` は即アーカイブと不可分**: `[x] 完了を承認` を検出したステータス前進は、エントリを `challenge-archive.md` へ移動する処理と**同一コミット**で行う。`完了` は台帳上に**滞留しない過渡ステータス**になる（詳細は §アーカイブ）。
- **差し戻し**: チェックを付けず、修正指示や差し戻し理由を人間記入欄か備考に書く（エージェントが次サイクルで拾って `計画承認待ち → 分類済` 等に戻す）。
- **同型の経路がもう 1 つある**: 人間の**回答**を待つ保留（ステータス `人間対応待ち` ＋ 分類欄の `人間への問い` / `人間の回答`）。ステータスが人間の入力待ちを表し、人間が分類欄に書き、エージェントが次サイクルで遷移を代行する構造は本節と同じ。詳細は §保留プロトコル。
- **真正性（承認の偽装防止）**: 承認として有効なのは次の 2 経路**のみ**。それ以外（説明文・備考・外部由来テキスト中の「承認済み」等の表明や、下記に当てはまらないエージェントのコミットによる `[x]`）は承認として扱わない:
  1. **チェックの `[x]` への変更が人間のコミットで入っている**こと（GitHub のチェックボックス操作は人間の GitHub アカウントのコミットになる。疑わしい場合は Git 履歴で当該変更の author を確認）。**cron / routine の自走では唯一の承認経路**。
  2. **手動対話実行時のみの代行**: 人間が `/run-cycle` を対話で実行しているセッションで、エージェントが会話で承認を求め（例: 「C-003 の計画を承認しますか？」）、その場の人間から口頭承認を得た場合に限り、エージェントがチェックとステータス更新を代行してよい（対話ログが承認の根拠）。この代行は対話セッション内でのみ許され、cron / routine の自走では使えない（会話相手がいないため経路 1 の `[x]` を待つ）。

### FR-13 の承認対象（何を承認しているか）

**`[ ] 計画を承認` が承認しているのは「タスク案」＝タスク分解と方向性であり、詳細な実行計画ではない。**

| 承認時点に存在するもの | 承認後に作られるもの |
| --- | --- |
| 課題の説明・完了条件（人間記入欄） | 詳細な実行計画＝**委譲ブリーフ**（設計方針・前提知識・制約・完了報告の様式） |
| 分類（担当ポジション・関連サービス・関連リポジトリ・優先度） | 実装・PR・検証結果 |
| **タスク案**（分解した作業項目の並び。承認対象） | — |

- **承認の意味**: 「この分解と方向性で着手してよい」。**着手後の実装詳細まで承認したことにはならない**（詳細は委譲ブリーフで決まり、台帳には残らない。恒久記録は journal と Git 履歴）。
- **なぜブリーフ級の計画を承認前に要求しないか**: 委譲ブリーフの作成コストが承認前に発生し、差し戻されると丸ごと無駄になるため。承認を**粗いが安い**単位に置き、詳細は承認後に作る（FR-13 は「方向性のゲート」であり「実行計画のゲート」ではない）。
- **承認者が見るべき欄**: `タスク案`（何をするか）／`完了条件`（何が達成なら完了か）／`関連リポジトリ`（どこを触るか）。この 3 つで判断できない粒度のタスク案は、**書き手（run-cycle 手順2）の記入が粗すぎる**——差し戻し（チェックを付けず理由を備考へ）で分解をやり直させる。
- **差し戻しは「実装が気に入らない」ではなく「分解・方向性が違う」ときに使う**（実装への異議は FR-32〔完了承認〕か、新しい課題として起票する）。

## 保留プロトコル（`人間対応待ち`・[#116](https://github.com/masanami/claude-flywheel/issues/116)）

エージェントが**人間へ問いを上げて課題を保留する**ときの表現。設計の判断材料と 4 案の比較は [human-hold-representation.md](./human-hold-representation.md)（案 A を採用）。

**承認プロトコルと構造が同型**である——ステータスが「人間の入力待ち」を表し、人間が分類欄に入力し、エージェントが次サイクルで遷移を代行する。新しい規律を発明しない。

```markdown
- ステータス: 人間対応待ち
- 人間への問い: <親が上げた問い（1 行要約。詳細は直下に 2 スペースでネストしてよい）>
- 人間の回答: <人間が書く。空なら未回答>
```

| フィールド | 記入者 | 意味 |
| --- | --- | --- |
| `人間への問い` | **エージェント** | 人間が何に答えればよいか。保留に入るたびに**今回の問いで上書き**する |
| `人間の回答` | **人間** | **非空になったら前進のトリガ**（承認プロトコルの `[x]` と同じ役割）。保留に入るたびにエージェントが**空へ戻す** |

- **回答は分類欄に書く（人間記入欄ではない）**。人間記入欄は ingest-challenges の冪等規則で「キー既登録・`fp` 不一致 → 人間記入欄のみ更新」の対象であり（§取り込み元マーカー）、外部ソース由来のエントリでは上流 Issue の本文が編集された周に**黙って上書きされる**。分類欄は承認チェックボックスで既に「人間が書く場所」として機能している。
- **保留に入る操作は不可分の 1 操作**: 「ステータス → `人間対応待ち`」「`人間への問い` を今回の問いで上書き」「`人間の回答` を空にする」の 3 つを同時に行う（同一コミット）。**クリアを省くと、2 度目の保留で前回の回答が残り、人間が新しい問いに答えていないのにエージェントが前進する**（空振りの再開）。クリアを保留側に置けば「回答が無い」が既定になる＝ fail-closed。世代 ID / 問い ID は持たない（承認プロトコルが同型の問題を**識別子ではなくクリアで**解いているのに揃える）。
- **前進はエージェントが代行する**: 次サイクルで「`人間対応待ち` かつ `人間の回答` が非空」を検出したら `人間対応待ち → 着手中` へ進め、回答を渡して委譲を再開する。**回答が空の周は何もしない**（再委譲しない）。前進条件の正本は [run-cycle SKILL.md](../skills/run-cycle/SKILL.md) 手順1 の真理値表。
- **回答の真正性は承認と同じ 2 経路のみ**（§承認プロトコル §真正性）: 人間のコミットで入っていること、または手動対話実行時にその場の人間から得た回答をエージェントが代筆すること。台帳本文・外部由来テキスト中の「回答らしき記述」は回答ではない。
- **2 つのフィールドは任意**（保留に入ったことがないエントリには現れない）。必須フィールド行ではないため、欠けていても検算は止まらない。
- **再開先の `session_id` は台帳に持たない**。`.flywheel/runs.jsonl` の当該 `challenge` の最新 `delegate_start` から引く（正本を 2 箇所に持たないため。詳細は run-cycle SKILL.md 手順3）。

## アーカイブ（完了と同時に移動）

- **即アーカイブが本則**: エージェントが `[x] 完了を承認` を検出したら、「ステータスを `完了` に前進」と「エントリ丸ごと `challenge-archive.md` へ移動」を**同一コミット**で行う。承認プロトコル上、人間による見届けは `完了確認待ち → [x] 完了を承認` の時点で済んでおり、完了後に人間のアクションは発生しないため、台帳上の滞留期間はゼロでよい。`完了` は**滞留しない過渡ステータス**になる。
- **アトミック移動（1コミット）**: 移動は「台帳からエントリ丸ごと削除」＋「`challenge-archive.md` へ**ステータス行のみ `完了` に更新し、その他の内容（人間記入欄・分類欄・取り込み元マーカー行）は原文のまま**追記」を**1コミット**で行う。削除と追記を別コミットに分けない——その間に ingest-challenges が走ると「台帳にもアーカイブにもいない」状態が生まれ、外部ソースに残る同一課題が新規として再取り込みされる（ゾンビ復活・重複登録の穴になる）。
- **常にアーカイブ（削除しない）**: 外部ソース由来（取り込み元マーカーあり）でも手書き（マーカーなし）でも、完了エントリは**常にアーカイブへ移動**する（削除はしない）。取り込み元マーカーの有無で運用を分岐させない。**例外**: `github-issue` ソースの assignee ポリシー不適合による取り込み解除（着手前・未完了エントリのみが対象。§取り込み元マーカー）は、この「完了→アーカイブ」フローとは別の経路であり、削除しアーカイブへは移動しない（[ingest-challenges §4](../skills/ingest-challenges/SKILL.md) 参照）。
- **取り込み元マーカー行はアーカイブ側でも保持する**。ingest-challenges の再取り込み照合は**台帳＋アーカイブの両方**を対象にする（アーカイブ済み課題を「キー未登録＝新規」と誤認して再取り込みしないため。アーカイブ設計は冪等性と不可分）。
- **移動はエントリ境界（見出しパターン）で切り、前後で検算する**。行番号演算による移動は隣接エントリのマーカーを壊すため使わない（手順と検算コマンドは §台帳を機械で編集するときの規律）。**台帳とアーカイブの 2 ファイル更新は `mv` 2 回では原子的にならない**ため、同節「2 ファイル更新のトランザクション」のマーカー＋起動時復旧に従う（1 コミットに収める規律は、中断からの回収とは別の話であり両方必要）。
- **閾値ルールはバックストップ（正常系では発火しない）**: 即アーカイブが機能していれば台帳に `完了` エントリは滞留しない。手動編集などで `完了` エントリが台帳に残ってしまった場合の掃除規定として、「完了から 30 日経過、または完了エントリが 20 件超」を閾値に、次サイクルの整理（run-cycle 手順1）でエントリごと `challenge-archive.md` へ移す。「完了から 30 日」の**基準日は、当該エントリのステータス行が `完了` になったコミットの日時**とする（`git log` で該当行の変更を遡って特定）。台帳テンプレートへの完了日時フィールドの追加は行わない（バックストップは異常系の低頻度な掃除規定であり、正常系の台帳フォーマットを太らせない）。基準日の特定が煩雑な場合は、日数基準の判定を待たず**件数基準（完了エントリが 20 件超）のみでも発火**してよい。このときも上記アトミック移動・マーカー保持・常にアーカイブの各方針に従う。
- **将来の年次分割方針**: アーカイブが肥大した場合（目安: 数千行超）は、タスク別分割ではなく**年次分割**（`challenge-archive-2026.md` 等）とする。分割時は ingest-challenges の照合対象を `challenge-archive*.md` の glob に広げる。当面（数千行に達するまで）は 1 ファイル運用を維持する。

## 取り込み元マーカー（ingestion の冪等性）

外部ソースから取り込んだ課題（[ingest-challenges](../skills/ingest-challenges/SKILL.md)）は、分類欄に**取り込み元マーカー**を 1 行持つ。これで**同じ課題の再取り込みを冪等**にする（二重登録しない）。

```markdown
- 取り込み元: <source-id> / <外部キー>（取り込み: <YYYY-MM-DD>）<!-- fp:<フィンガープリント> -->
```

- **`<source-id>`**: 取り込み元（`challenge-sources.md` の `id`）。
- **`<外部キー>`**: ソース側の**安定 ID**（Notion page id / Slack ts / 見出し ID 等）。再取り込みの照合キー。
- **`fp:<フィンガープリント>`**: **人間記入欄**（説明・完了条件・緊急度）を正規化した指紋。人間は読まないので HTML コメントに隠す。**複数行フィールド（§複数行フィールドの記入形式）を含む場合の正規化規則の正本は [ingest-challenges §4](../skills/ingest-challenges/SKILL.md)**（算式が揺れると全エントリが毎周「更新あり」になるため決定的に定める）。
- 再取り込み時の判定（詳細は ingest-challenges §4）:
  - キー未登録 → **新規追記**（ステータス 未分類）。
  - キー既登録・`fp` 一致 → **スキップ**（変化なし）。
  - キー既登録・`fp` 不一致 → **人間記入欄のみ更新**し `fp`・取り込み日を更新。**分類欄は全項目を保持**（担当ポジション・関連サービス・関連リポジトリ・関連Issue・関連PR・優先度・ステータス・タスク案・承認チェック・備考。**この列挙は例示であり、規則は「人間記入欄と取り込み元マーカー以外は触らない」**＝分類欄に将来追加される項目も自動的に保持対象になる。内部正本の分類・進行を壊さない）。
- **マーカー無しの手書きエントリは ingestion の対象外**（触らない）。手書き運用と取り込み運用は共存できる。
- **ポリシー不適合エントリの取り込み解除**（`github-issue` ソースのみ）: マーカー一致で台帳に「キー既登録」のエントリについて、最新の `assignees` が現在の `assignee_policy` / `self_assignees` に合致しなくなった場合（他人が新たに assign された・`self-only` で unassigned になった等）、**人間承認前・実作業が未着手**（未分類／分類済／計画承認待ち〔未承認〕）のエントリはアーカイブへ移動せず**台帳から丸ごと削除**する（マーカーごと消える。アーカイブに残すと assign 解除後の再取り込みが「既登録」と誤判定されるため）。**着手中以降（承認済み含む）**のエントリは自動削除せず、ingest-challenges のレポートへ「要対応」として残す（台帳・分類欄は変更しない）。アーカイブ側でマーカーが一致した場合はこの判定の対象外（アーカイブは完了フローの正本のため変更しない）。詳細・判定基準は [ingest-challenges §4](../skills/ingest-challenges/SKILL.md) 参照。

## 台帳を機械で編集するときの規律（マーカー保全）

取り込み元マーカーは**冪等性の要**であり、壊れると二重取り込み・復元不能を静かに引き起こす。実運用で、エントリ移動を**行番号演算**で行った結果、隣接エントリのマーカーを巻き込んで壊した事例がある（2026-08-17 に検出・修復）。エージェントが台帳を編集する手順（ingestion の追記・更新、§アーカイブのアトミック移動、取り込み解除の削除）は、次を必ず守る。

> **実行時の写しはスキル本文にある**（[run-cycle](../skills/run-cycle/SKILL.md) 手順0 の復旧・手順4 の移動手順）。**逐語の重複は意図したもの**で、集約すると headless 委譲で規約が届かなくなる（[runtime-text-conventions.md](./runtime-text-conventions.md) §3・§4）。本節を変えたらスキル側の写しも同時に更新する。
>
> **この規律自体が新たな事故を生まないこと**: 失敗時の復旧に `git checkout -- challenge-ledger.md` のような**ファイル全体を戻す操作を使ってはならない**。台帳には人間が直接書き込む欄（人間記入欄・承認チェック）があり、機械編集より前から**未コミットの人間の変更が同居しうる**。ファイル全体を戻すとそれを巻き添えで破棄する。**元ファイルを一度も書き換えない（一時ファイル方式）ことで、そもそも復旧操作を不要にする**。

1. **エントリ境界は見出しパターンで切る**。`^### \[` にマッチする行を境界とし、**行番号のオフセット計算でエントリを移動・削除しない**。
2. **編集は一時ファイルに対して行う**。`challenge-ledger.md`（およびアーカイブ）を直接書き換えず、同じディレクトリに一時ファイル（例: `challenge-ledger.md.tmp`）を作り、そこに編集後の全文を書く。元ファイルはこの時点では無傷のまま。
3. **一時ファイルに対して検算する**。各エントリの取り込み元マーカーが高々 1 つであること、エントリ総数が期待値と一致することを確認する:

   ```bash
   awk '
     /^```/ { fence = !fence; next }
     fence { next }
     /^### \[/ { if (h != "") check(); h = $0; t = 0; n++ }
     /^- 取り込み元: *[^ ]/ { t++ }
     END { if (h != "") check(); printf "entries=%d ng=%d\n", n, ng }
     function check() { if (t > 1) { ng++; print "NG: " h } }
   ' challenge-ledger.md.tmp
   ```

   期待値は `ng=0` かつ `entries` が「編集前の値 ± 意図した増減」と一致すること。**編集前の値は同じコマンドを元ファイルに対して実行して実測する**（比較の基準を思い込みで置かない）。

4. **検算に成功した一時ファイルだけを元ファイルへ置換する**（`mv challenge-ledger.md.tmp challenge-ledger.md`）。同一ディレクトリ内の `mv` は原子的に置き換わるため、中途半端な内容が見える瞬間が無い。
5. **検算に失敗したら一時ファイルを捨てるだけ**にする（`rm challenge-ledger.md.tmp`）。元ファイルは一度も書き換えていないので**復旧操作は不要**であり、**`git checkout` 等でファイル全体を戻してはならない**（人間の未コミット変更を破棄するため）。検算結果を添えて報告し、コミットはしない。
6. **アーカイブへの移動を伴う操作では、移動元（台帳）と移動先（`challenge-archive.md`）の双方を一時ファイルで作り、双方の検算に成功してから双方を置換する**。ただし **`mv` が原子的なのは 1 ファイル単位であり、2 回の `mv` は原子的ではない**。途中で停止すると片方だけ適用された状態が残るため、下記「2 ファイル更新のトランザクション」に従う。

### 2 ファイル更新のトランザクション（アーカイブ移動・**復旧可能にする**）

2 回の `mv` の間でプロセスが停止すると、「台帳から消えたのにアーカイブに無い」（**消失**）か「両方にある」（**重複**）が残る。次回実行がその状態を読むと、重複登録または課題の欠落が起きる。一時ファイル方式は人間の未コミット変更を守るが、**2 ファイル間の整合は守らない**。そこで**トランザクションマーカー＋起動時復旧**を課す:

1. **マーカーを書く**（置換の前）。`.flywheel/ledger-tx.json` に、これから行う移動を記録する（`.flywheel/` はローカル・gitignore 対象）:

   ```json
   {"op":"archive","entries":["C-012"],"ledger_tmp":"challenge-ledger.md.tmp","archive_tmp":"challenge-archive.md.tmp","started_at":"<ISO8601>"}
   ```

2. **追記側を先に置換する**（`mv challenge-archive.md.tmp challenge-archive.md` → `mv challenge-ledger.md.tmp challenge-ledger.md`）。**順序は必須**: この順なら途中停止で残るのは「両方に存在」＝**重複**であり、検出も回収も可能。逆順だと「どちらにも無い」＝**消失**になり、一時ファイルが失われていれば回復できない。
3. **両方の `mv` が終わったらマーカーを削除**する。コミットは**マーカー削除後**に行う（Git 上は削除と追記で 1 コミット）。

**起動時復旧（台帳を触るすべての手順の冒頭で実施・fail-closed）**: `.flywheel/ledger-tx.json` が存在したら、**新しい編集を始める前に**前回の中断を回収する。マーカーの `entries` の各 ID について、台帳とアーカイブの実状態を見て次のとおり判定する。**判定は全 ID について読み取りだけで先に済ませ、1 件でも最終行（消失）に該当したら台帳・アーカイブ・マーカーのいずれにも書き込まずに停止する**（先頭の ID から順に復旧すると、後続 ID の消失に気付く前に書き込みが済んでしまう）:

| 台帳 | アーカイブ | 状態 | 復旧 |
| --- | --- | --- | --- |
| あり | あり | 手順 2 の 1 回目だけ適用（**重複**） | 台帳側から当該エントリを削除して移動を完了させる（アーカイブが正）。同節 1〜5 の一時ファイル方式で行う |
| なし | あり | 移動は**完了済み**（マーカー削除の前に停止） | マーカーを削除するだけ |
| あり | なし | 移動は**未適用** | マーカーを削除し、通常フロー（次回の完了承認検出）に委ねる |
| なし | なし | **消失**（想定外） | **台帳の編集を一切行わず停止**し、人間へ報告する。マーカーの内容・当該 ID・直前のコミットを添える（データ消失の可能性があり、機械が推測で復元しない） |

- **マーカーが残っている間は新しい台帳編集を開始しない**（回収してから進む）。回収できない行（上表の最終行）を検出した場合も同様に停止する。
- 復旧の実施有無と結果は報告に含める（黙って直さない）。

## 既存ワークスペースの移行（テンプレート追従・Issue #88）

テンプレートが更新されても、**既に scaffold されたワークスペースの台帳は自動では追従しない**（[flywheel-init](../skills/flywheel-init/SKILL.md) は「既存を上書きしない」冪等 scaffold のため）。実際に、タスク案行・承認チェックボックス行の追加（PR #39）に 2 エージェントが追従できず、3 エージェントで 3 通りの形に分岐した（Issue [#87](https://github.com/masanami/claude-flywheel/issues/87)）。追従は [`scripts/migrate-workspace.rb`](../scripts/migrate-workspace.rb)（flywheel-init の再実行から呼ばれる）が行う。

### 自動適用するもの／しないもの（線引きと根拠）

| 分類 | 対象 | 扱い | 根拠 |
| --- | --- | --- | --- |
| **構造マイグレーション** | `challenge-ledger.md` / `challenge-archive.md` | **自動適用**（dry-run で提示 → `--apply`） | テンプレート由来の構造と**運用中のライブデータ**が同居する唯一のファイル。ファイル単位の再生成が不可能で、構造変換でしか追従できない |
| **追記/マージで対応済み** | `CLAUDE.md`・`.claude/settings.json`・`.gitignore` | flywheel-init の既存手順（手順2・手順3）が担当。移行スクリプトは**不足の検出のみ** | 既に追記/マージの規定があり、二重実装にしない |
| **単純なコピー物** | `runtime/README.md`・`journal/README.md`・`journal/cycle-template.md`・`container/Dockerfile`・`container/compose.yml` | **検出のみ**（テンプレートとのバイト差分を報告し、自動上書きしない） | テンプレート版マーカーを埋めていないため、機械には「テンプレートが更新された」と「利用先がカスタマイズした」の区別が付かない。自動上書きは利用先の編集を静かに壊す。マーカー方式を採らないのは、台帳の機械編集規律（§台帳を機械で編集するときの規律）と別系統の版情報を増やさないため |
| **触らないもの** | `journal/` の実体・`memory/`・`positions/`・`.flywheel/cadence.json`・`repos.tsv`・`priority-policy.md` | 対象外 | 運用データ・利用先固有の設定であり、テンプレートは初期値でしかない |

### 台帳・アーカイブに対して行う変換

1. **記入例（テンプレート部）の現行化**（台帳のみ）。旧形式の記入例（HTML コメントで囲った形・フェンス形）を現行テンプレートの記入例ブロックへ差し替える。アーカイブは記入例を持たないため対象外。**削除してよいのは「既知テンプレート由来と証明できた行」だけ**（下記 §削除は出所で証明する）。
2. **欠落フィールド行の補完**（分類欄のみ）。`タスク案` / `承認（人間がチェック）` ＋チェックボックス 2 行 / `備考` / `担当ポジション` / `優先度` / `ステータス` を正規順序の位置へ**空値で挿入**する。挿入先は**分類欄見出し直後の連続したフィールド並びの中**に限る（記入例の残骸が末尾に紛れているエントリで、分類欄の外へ承認行を置かないため）。**人間記入欄のフィールドは補完しない**（機械が人間の欄を捏造しない）——欠落は報告に留める。
3. **参照フィールドの追加**（**台帳のみ**）。`関連リポジトリ` / `関連Issue` / `関連PR` を空値で追加する。**アーカイブには追加しない**——これらは run-cycle が計画時・PR 作成時に埋める欄であり、完了済みエントリでは埋まらない（原文保存の履歴を無駄に書き換えない）。
4. **形 E（太字見出しブロック）の正規化**。`**タスク案（FR-13・承認済み …）**` ＋行頭の番号付きリストを、分類欄の `- タスク案:` ＋ 2 スペースのネスト項目へ変換する。**旧見出しの文言は HTML コメント（`<!-- 移行前の記載（#88）: … -->`）として保全**し、失わせない。**変換は全項目を尽くせるときだけ行う**——ブロックに番号付き項目以外の行（注記・記入例の残骸等）が混じっていれば、どこまでがタスク案かを機械が決められないため**一切変換せず**人間判断へ倒す（部分変換を「変換した」と報告すると承認対象の中身が欠落し、Issue #87 の症状を再生産する）。
5. **旧ラベルの改名**。`- 承認:` → `- 承認（人間がチェック）:`（チェック状態には触れない）。**分類欄セクションに属する行だけ**が対象（人間記入欄が分類欄の後ろにある構成でも、人間の自由記述を書き換えないため。区分は見出しへの帰属で判定し、行の位置関係を仮定しない）。

**アーカイブの原文保存（§アーカイブ）との関係**: 原文保存が禁じているのは「完了エントリを移動するついでの修復」であり、**#88 の一度きりの構造マイグレーションはその例外**として扱う（本節が根拠）。移行対象は「フィールド行の追加」と「同じ内容の形の付け替え」に限り、記入された値は書き換えない。

**改行コード**: CRLF のファイルは CRLF のまま出力する。CRLF と LF が**混在**するファイルは、どちらへ寄せても人間の意図を壊しうるため**移行しない**（理由を報告する）。

### 承認（`[x]`）は機械が代筆しない・無効化もしない

旧形式では承認事実が見出し文言（`**タスク案（FR-13・承認済み 2026-07-05）**`）や「アーカイブ済み＝完了承認を経ている」という文脈にしか無いことがある。移行は**常に未チェックで新設**し、手がかり（旧見出しの文言・ステータス）を添えて「人間判断が必要」へ列挙する。§承認プロトコル §真正性が認める承認経路は人間のコミットと対話代行の 2 つだけであり、**移行スクリプトはそのどちらでもない**。

**逆向きの事故（承認の無効化）も禁じる**: 既存のチェック行が正規形（行頭に半角スペース 2 個＋ラベル前方一致）でない場合——インデントが 4 スペース、ラベルが旧表記（`計画承認`）等——「チェック行が無い」と誤認して未チェック行を足すと、**既存の `[x]` が実質無効化される**（消費側は正規形の行を見るため）。移行は**チェック行らしき行を広く検出**し、正規形でないものが 1 つでもあれば**そのエントリの承認欄には一切手を出さず**人間判断へ倒す。

### 削除は出所（provenance）で証明する

**範囲判定のヒューリスティックを検算の期待値にも使うと、範囲を誤認したときに検算が空虚に真になる**（誤って消した行が「消す予定だった行」に化ける）。実際、記入例の見出しを前方一致で探すと `## 記入例の運用メモ` のような**人間が書いた別セクションを丸ごと無言削除**し、削除範囲を両側から除外して比較する検算はそれを検出できなかった。

そこで移行は、**削除する行が既知テンプレート由来であることを独立に証明**する:

- **既知集合** = 現行テンプレートの記入例ブロック ∪ 過去テンプレートの記入例ブロック（[`scripts/migrate-workspace.rb`](../scripts/migrate-workspace.rb) 末尾の `DATA` に同梱）。
- 記入例と判定した範囲に**既知集合に無い行が 1 行でもあれば削除しない**（人間の書き足し・独自フェンス・別セクション）。理由と該当行を報告し、人間が差し替える。
- 検算でも同じ集合を使い、**実際に消えた行がすべて既知集合に属すること**を確認する（範囲計算のバグをここで捕まえる）。
- **テンプレートの記入例を変更したら、変更前の行を `DATA` へ追記する**（追記漏れはテストが検出する）。

### 非破壊の担保（台帳の機械編集は事故の実績がある）

エントリの範囲削除が隣接エントリの備考行・空行を巻き添えにした事故が実際に 2 回起きている。移行はこれを構造的に防ぐ:

1. **一時ファイル方式**（§台帳を機械で編集するときの規律）。元ファイルを直接書き換えず、検算に通った内容だけを置換する。検算用の候補はワークスペース**外**（TMPDIR）に置き、置換用の一時ファイルは**どの経路で中断しても必ず後始末する**（失敗時にワークスペースへ残骸を残さない）。
2. **出所の検証**（上記 §削除は出所で証明する）。
3. **全行の差分の検算**。ファイル全体で「消えた行・増えた行」を多重集合で求め、**計画した操作で説明できる行だけ**であることを要求する（削除範囲を除外しないので、範囲誤認・想定外の欠落がここに現れる）。あわせてエントリ単位でも同じ照合を行い、誤りの位置を示す。
4. **バリデータによる前後比較**。[`validate-artifact.rb`](../scripts/validate-artifact.rb) を移行前・移行後の候補に掛け、**移行後の違反が移行前より増えていない**ことを**多重集合**で要求する（集合の差だと、同じ文言の違反が増えても見逃す）。**dry-run でも実行する**——「dry-run は通ったのに `--apply` で失敗する」を無くすため。
5. **バックアップ**（`.flywheel/migration-backup/<timestamp>/`。**既存ファイルは上書きしない**＝世代を失わせない）と**冪等**（2 回目は差分ゼロ）。
6. **範囲の誤認に対する安全ガード**。記入例と判定した範囲に実エントリらしい行（プレースホルダでない見出し・2 つ以上の見出し）があれば**手を出さず人間へ報告する**（記入例コメントの閉じ忘れで実エントリが「検査対象外」に落ちている台帳を、範囲削除で消さないため）。
7. **記入例のサンプル行を実データと混同しない**。台帳末尾の記入例はフェンス／HTML コメントの中にあり、最終エントリの本文に含まれる形が実在する。フィールドの存在判定・重複計数は**フェンス・コメントの外の行だけ**を対象にする。

**自動では直さないもの**（人間判断へ倒す）: 見出しの破損・記入例ブロックの残骸によるフィールド行の重複、人間記入欄の欠落、タスク案の太字見出しに項目以外の行が混じる形、正規形でない承認チェック行、記入例に人間が書き足した行、改行コードの混在。これらは「どこからどこまでが壊れているか」「どちらが人間の意図か」を機械が決められない。

## 優先度判定の基準（外出し先）

分類欄の `優先度: P0 | P1 | P2` 欄自体のフォーマットは変更しない。**判定基準・着手順の選択基準**は各エージェントの `priority-policy.md`（雛形 [`templates/priority-policy.md`](../templates/priority-policy.md)）に外出しする。`run-cycle` 手順1・手順2 がこれを参照する（不在時は現状どおりエージェント裁量）。詳細は [`skills/run-cycle/SKILL.md`](../skills/run-cycle/SKILL.md) を参照。

## 運用メモ

- 人間は**共有ソース**に書き、各エージェントが自分に関係する分だけ取り込む。共有ソースの実体は差し替え可能で、外部ドキュメント（Notion/Doc/Slack 等）化は [ingest-challenges](../skills/ingest-challenges/SKILL.md) が担う（[requirements.md OQ-01](./requirements.md) / architecture AO-06）。取り込み元の宣言は `challenge-sources.md`（雛形 [`templates/challenge-sources.md`](../templates/challenge-sources.md)）。
- 「分類欄」はエージェントが更新するため、人間がするのは「人間記入欄」の記述と**承認チェック**（§承認プロトコルの `[x]` タップ）だけでよい。
- ステータスや担当の更新履歴は Git の差分で追える。
