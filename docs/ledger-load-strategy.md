## 0. 要旨

1. **台帳の 65.1% は「説明の原文引用」1 フィールドである**（31,242 tok 中 20,339 tok）。
   エントリ本文だけを分母に取れば 67.7%。アーカイブでも同じ比率（65.2%）で、
   これは一時的な偏りではなく**構造的な内訳**である（§1.3）。
2. **案 1（ステータスによる絞り込み）は、そのままでは削減量ゼロになる**。
   7 ステータスすべてが、いずれかの手順の対象として生きているためである（§2.3）。
   削減は「どのエントリを読むか」ではなく「**各エントリのどこまで読むか**」で決まる。
3. **索引は 1 エントリ 78 tok で作れる**（全 11 エントリで 860 tok ＝ 全文 31,242 tok の
   **2.8%**）。実際に投影スクリプトを書いて実測した（§3.2）。1 エントリあたり
   2,731 tok → 78 tok で、**35 分の 1** になる。
4. **案 2 は「索引ファイルを持つ」形で実装してはならない**。それは
   「索引と本体を同期させる」構図になり、`sync-free` 不変条件に反する。
   **索引は台帳から毎回投影する**（ファイルを作らない・stdout のみ）形にすれば、
   正本は台帳 1 つのままで、フォーマット契約・board パーサ・`fp` への波及が
   **すべてゼロ**になる（§4）。
5. **案 3（原文引用を台帳から外す）は、既に一度潰した欠陥を再生産する**。
   ingest-challenges の `fp` 規定は「引用行を必ず含める」ことを明文で要求しており、
   外すと**外部 Issue の本文だけが編集されたとき更新検知が永久に効かなくなる**
   （skills/ingest-challenges/SKILL.md の当該規定が、その失敗をそのまま記述している）。
   さらに board のカード詳細が `-` 相当の表示に退行し（実コードで確認）、
   アーカイブの恒久記録から 65.2% が失われる（§3.3）。
   **案 2 とほぼ同じ削減量を、これらの破壊なしに得られる**。
6. **案 4（母数の削減）は継続すべきだが、基準線としては不十分**。
   `assignee_policy: self-only` への切り替えによる剪定コミット `6dc6344` は
   台帳を **42,207 → 28,098 tok（−33.4%）** に落としたが、**同じ日の 1 時間 43 分後**の
   `aa0ac68` では既に **31,242 tok（+3,144）** に戻っている（§1.4）。
   一度きりの剪定は、外部 ingest の流量に対して持続的な制御にならない。

## 2. 手順1・手順2 が必要とする判断材料（フィールド粒度）

### 2.1 現在の規定

手順0 は台帳の読み方を次の一文で規定していた（**実装前**の `skills/run-cycle/SKILL.md`＝`5024ec8`。
現在は §5「実測結果」のとおり投影スクリプトの呼び出しに置き換わっている）:

> ベースライン（ポジション要約・記憶 INDEX・recall 手順）は `CLAUDE.md` として**自動ロード済み**。
> 加えて `challenge-ledger.md` をロードし、**詳細記憶は手順2の recall で関連分だけ**引く。

「ロード」に範囲の限定はなく、**絞り込みを許す規定も存在しない**。一方で
手順1〜4 の対象は見出しレベルでステータスに絞られている
（手順1「対象: ステータス『未分類』」、手順2「対象: ステータス『分類済』」…）。
**対象は絞られているのに読み込みは絞られていない**、というのが現状である。

**含意**: 全文が要るのは (i) **未分類エントリ**（1-a/1-b/1-d/1-e）と
(ii) **その周に実際に着手する 1〜数件**（2-e/2-f/2-g）だけである。それ以外の規定は
索引または `git log` で足りる。手順3（実行）は対象エントリのみを、手順4（検証）は
アーカイブ移動時に対象エントリの原文を必要とし、いずれも**他エントリを参照しない**
（`skills/run-cycle/SKILL.md` の手順3・手順4 に横断参照の規定は無い）。

**例外は 1-h（差し戻しの検出）**——備考は 1 エントリ平均 230 tok あり索引には載らない。
承認待ちエントリの備考が人間に書き換えられたかは、全文ロードではなく
**前周から当周までに限った差分**で拾うのが安い:

```bash
git diff <前周の基準SHA>..<当周の検査対象SHA> -- challenge-ledger.md
```

**範囲は必ず両端の SHA で閉じる。** `git log -p -- challenge-ledger.md` のような
範囲無制限の形は使わない——ファイルの全履歴を出すため、過去の修正まで毎周の
差し戻し候補として再浮上し、出力量も履歴の長さに比例して増える（毎周走る手順で
これは「削減」の反対側に効く）。

**ただし現時点で前周の基準 SHA を持つ経路は無い**（実コードで確認: `runs.jsonl` の
`cycle_start` / `cycle_end` は `ts` / `cycle` / `result` のみ、`journal/index.jsonl` は
`date` / `seq` / `touched_issues` / `delegations` / `pr_urls` / `pending_approvals` /
`decisions` のみで、いずれも SHA を持たない。`run-cycle` 手順6 の `git rev-parse HEAD` は
控えた値をサイクルレポートに出すだけでファイルへ永続化しない）。
`git log --grep` でコミットメッセージの慣習から拾う経路は在るが、
散文の慣習であって機械可読な契約ではなく、サイクル間に挟まる差し込みコミットも
拾えない。**この値を持つ必要がある**ことを §8 D-6 に未決として残す。

§3.2 のコスト表は、この**範囲限定の差分**の取得を計上していない（変化のあった行だけが
出るため、本ドキュメントの比較を左右する規模にはならないが、**計上していない事実は
明示しておく**）。

### 2.3 「ステータスで絞る」が単独では効かない理由

7 つのステータスすべてが、いずれかの手順の**対象**として生きている:

| ステータス | 消費する規定 |
| --- | --- |
| 未分類 | 手順1（整理）の対象 |
| 分類済 | 手順2（計画）の対象 |
| 計画承認待ち | 手順1-f（`[x] 計画を承認` の検出 → 着手中へ前進） |
| 着手中 | 手順3（実行）の対象 |
| 検証中 | 手順4（検証）の対象 |
| 完了確認待ち | 手順4 FR-32（`[x] 完了を承認` の検出 → 完了＋即アーカイブ） |
| 完了 | 手順1-i（アーカイブ・バックストップ） |

**どのステータスも捨てられない**。したがって「当周に扱いうるステータスのエントリだけを読む」
という案 1 の素朴な形は、**削減量ゼロ**になる。削減は「読むエントリを減らす」ことでは
なく「**1 エントリあたりの読む量を減らす**」ことからしか出ない——つまり案 1 は案 2 に
吸収される（§3.1）。

### 2.4 着手順の選択基準は**モード依存**である（案 1・案 2 の設計制約）

`priority-policy.md` の各モードが「着手順の選択基準」で参照するものを、全 6 モードについて
実測した（`aa0ac68` 時点・`active: normal`）。索引は §3.2 の 10 列:

| モード | 着手順が参照するもの | 索引で足りるか |
| --- | --- | --- |
| `normal`（現在 active） | 優先度（P0→P1→P2）→ 同一優先度内は**起票日が早い順** | **✓**（優先度・起票日） |
| `gdd-first` | 明示された課題 ID の列挙と依存順 | **✓**（ID） |
| `improvement-first` | 明示された課題 ID の列挙と依存順、「同一リポジトリ・同一ファイル群に触れる組は 1 委譲に束ねてよい」 | **✓**（ID・関連リポジトリ） |
| `gdd-dogfood-first` | 「**静かに壊れるものを先に着手する**」「失敗が観測されない欠陥」 | **✗ 内容判断が要る** |
| `release-freeze` | 「回帰修正・本番安定に関わるか」「新規機能追加系か」 | **✗ 内容判断が要る**（タイトルで概ね判定できるが確実性は説明依存。§7 の D-2 決定により fail-closed 側＝全文へ倒す） |
| `domain-bootstrap:<domain>` | `<domain>` に関連するか | **✓**（関連サービス・担当ポジション） |

**6 モード中 4 つは索引だけで着手順を決められる**。残る `gdd-dogfood-first` と
`release-freeze` はエントリの**内容**を読まないと基準を適用できない。
設計上の要件は:

> 索引だけで着手順が決まらないモードでは、**分類済エントリの全文を開く**（fail-closed）。
> 索引が無い今より悪くなることはない（今は全モードで全件を無条件に読んでいる）。

`domain-bootstrap:<domain>` は **`関連サービス` を索引に載せることではじめて成立する**——
この列が無い索引では同モードの着手順を判定できない。同様に 2-d（assignee 再照合）は
**`取り込み元` の有無**を必要とする。両者は §3.2 の投影に含めてある。

### 3.3 案 3 — 原文引用の置き場所（台帳から外し参照に寄せる）

- **(a) 削減見込み**: 引用行（`^>`）を物理的に削除した台帳を**再トークン化して測ると**
  エントリ本文 9,697 ＋ ヘッダ 1,204 ＝ **10,901 tok（−65.1%）**、
  固定文脈は 35,194 ＋ 10,901 ＝ **46,095 tok（−30.6%）**。
  案 2 の 0〜3 件シナリオ（−33.4%〜−45.7%）と**同等かやや劣る**。
  （§1.3 の内訳から引き算した概算 30,038 − 20,339 ＝ 9,699 とは 2 tok 差で一致する。
  本項は概算ではなく実テキストの再トークン化を採った。）
- **(b) 判断材料の充足**: **欠ける**。1-a/1-b/1-d/1-e（分類・優先度判定）と
  2-e（タスク分解）が必要とするのは説明の**内容**である。参照だけになると、
  読むために毎回 `gh issue view` 等の外部取得が要る——それは案 2 の
  「必要な 1 件だけ開く」と同じ動作を、**外部ネットワーク依存・外部の可用性依存で**
  やることになる。案 2 の方が安全側である。
- **(c) フォーマット契約への波及**: 中程度。`LEDGER_REQUIRED_LINES` の `- 説明:` 行自体は
  残るので必須行検査は通る。ただし **`- 説明:` の値が常に `（原文引用）` という定型文字列に
  なる**ため、契約は「値があること」を検査していない現状では**空虚に真**になる
  （値の実質を検査していないので、壊れても契約が気付かない）。
- **(d) board への波及**: **視認できる退行が起きる**。
  `src/ui/components/CardDetailModal.tsx:310` は `{challenge.description ?? "-"}` で
  説明を表示する。パーサ（`src/server/parsers/ledger.ts`）は引用行を継続行として
  `description` に取り込む設計（`QUOTE_CONTINUATION_PATTERN = /^>/`）なので、引用を外すと
  **カード詳細の説明欄が `（原文引用）` の一語だけになる**。これは Issue #87 /
  claude-flywheel-board#151 で問題になった「値が落ちて `-` 表示になる」事故と同型である。
- **(e) `fp` 算出への影響**: **冪等性が壊れる。しかも既に一度潰した欠陥の再生産である。**
  `skills/ingest-challenges/SKILL.md` の `fp` 規定は次を明文で要求している:

  > **引用行を必ず含める**: 本スキルが書く説明欄は `- 説明:（原文引用）` ＋ **直下のブロック引用**
  > であり（実運用の主要形）、引用行を値から外すと説明の値が常に定型文字列 `（原文引用）` に
  > なる。すると**外部 Issue の本文だけが編集されたとき fp が動かず、永久にスキップされて
  > 人間記入欄が更新されない**（更新検知の不在を「変化なし」の証明に使わない）。

  さらに、`fp` 不一致時の自己修復条項——「**正規化済み本文同士を直接比較して実質同一なら**
  人間記入欄・取り込み日は更新せず `fp` のみ更新する」——は、**台帳側に旧本文が残っている
  ことを前提**にしている。引用を外すと比較相手が消えるため、この条項が機能しなくなる。
  `fp` を「取得した外部本文から算出する」形へ作り替えれば技術的には成立するが、
  **台帳だけからは `fp` を再計算・監査できなくなる**（現在は 8/8 の既存 `fp` を台帳から
  再現できることが実測済み＝[ingest-deterministic-fp]）。
- **(f) 恒久記録の喪失**: 手順4 の即アーカイブは「ステータス行以外は**原文のまま**追記」と
  規定されている。引用を外すと `challenge-archive.md` にも参照しか残らない。
  現在アーカイブは 57 エントリ・89,229 tok あり、そのうち **58,186 tok（65.2%）が引用**である。
  外部 Issue が編集・削除されれば、この 65% 相当の根拠が**回復不能に失われる**。
- **(g) `ingest-body-blockquote` の防御**: 引用を外せば「本文中の `##` が台帳のエントリ構造を
  壊す」経路自体が消えるので、その防御は不要になる。**ただし**参照だけを置く形でも
  タイトルを転記するなら、タイトル中の `#` に対する同種の防御は残す必要がある。

**採否: 不採用。** 削減量は案 2 と同等以下でありながら、`fp` の更新検知・board の表示・
アーカイブの恒久記録という 3 つを同時に壊す。**案 2 は同じ削減量をこれらの破壊なしに得る。**

### 3.4 案 4 — 母数の削減（`assignee_policy: self-only`）

- **(c)(d)(e)**: 波及なし（運用設定の変更であり形式・契約・`fp` に触れない）。

## 6. 構造不変条件テストの設計（実装より先に入れる）

`run-cycle` は毎周走る中核であり、散文仕様は型検査が効かない。**変更前にテストで固定する**
（§7 の決定）。以下は設計案であり、実装は本ドキュメントの範囲外。

| # | テスト | 何を防ぐか |
| --- | --- | --- |
| T1 | **経路表の完全性**: 「ステータス × 手順 → 索引で足りる / 全文が要る」の真理値表を持ち、`LedgerStatus` の 7 値すべてに行があることを検査する。行の無いステータスは **fail**（fail-closed） | ステータスを足したとき、どの手順がそれを読むか未定義のまま出荷される |
| T2 | **投影の全域性**: 投影スクリプトの出力行数 ＝ 台帳のエントリ数（`^### \[`・フェンス除外）。1 件でもずれたら fail | 索引が課題を静かに落とす（[ledger-range-delete-bug] と同型の見落とし） |
| T3 | **受理方向**（[generator-validator-shape-mismatch] 対策）: `contracts/fixtures/ledger/valid/*` の全正例に対して投影が exit 0 かつ全エントリを出力すること | 「自分の正規出力を自分が受理しない」欠陥 |
| T4 | **単一エントリ抽出の境界**: `^### \[<ID>\]` から次の `^### \[` までの抽出が、隣接エントリの行を 1 行も含まないこと。**変異注入**（境界の直前・直後に行を足す）で検出できることまで確認する | 隣接エントリの巻き込み（[ledger-range-delete-bug]・再発 2 回） |
| T5 | **否定検査**: 投影の出力に引用行（`^>`）が 1 行も含まれないこと。含まれたら fail | 索引が肥大して「索引である」という前提が静かに失われる |
| T6 | **`sync-free` の固定**: 索引がファイルとして生成されないこと（`contracts/cycle-commit-paths.txt` に索引パスが現れない・`git status` に新規パスが出ない） | 索引ファイル化への漂流＝二重正本の発生 |
| T7 | **語彙駆動の結線**: `LedgerStatus` の 7 値を正本（例: `contracts/` の 1 ファイル）から読み、SKILL.md の手順見出しの「対象: ステータス『…』」と T1 の表が同じ語彙を使っていることを検査する | 3 箇所（board 型・SKILL.md・表）のずれ |
| T8 | **列の完全性**: §2.2・§2.4 が「索引で足りる」と宣言した規定・モードが必要とするフィールドが、投影の出力列にすべて存在すること（`関連サービス`・`取り込み元の有無` を含む） | 判定に要る列が索引から抜け、モードの着手順が決められなくなる（本 PR のレビューで実際に検出された欠落） |
| T9 | **実測表の自己整合**（本 PR のレビューで検出）: §1.1 が宣言した SHA で §1.2 が実際に測られているかを**バイト**で照合し（tok と違いトークナイザ非依存＝`git show \| wc -c` で検算できる）、あわせて表の内部整合（各行の合計＝小計セル／派生定数＝小計−台帳／§5 の before＝§1.2 の小計）を検査する | 版を宣言していたのに別の版の値が入り、そこから導いた十数個の派生値がすべてずれる（宣言と実測の突き合わせが手作業だったため） |

T1・T7・T8・T9 は散文・ドキュメントの検査、T2〜T6 は投影スクリプトの単体テスト。
**実装では全 9 項目を `scripts/tests/ledger-index.test.sh`（91 assertions）に置いた**——
1 ドキュメントのために 10 個目のスイートを増やすより、機能の契約と同じ場所で守るほうが
見落としにくいため。T9 がワークスペース側のファイル（`aa0ac68` の台帳等）を照合できないのは、
それが別リポジトリにあり本リポジトリから参照できないからで、そちらは表の内部整合で守る。

## 7. 採否（**人間が確定済み**）

| 案 | 採否 | 根拠（実測値） |
| --- | --- | --- |
| **1. ステータスによる絞り込み** | **不採用**（案 2 へ吸収） | 素朴な形では削減 **0 tok**（7 ステータスすべてが手順の対象。§2.3）。精密化した値 20,464 tok は案 2 の最悪ケースと一致し、実体が案 2 であることを示す |
| **2. 索引 ＋ 必要分だけの読み出し** | **採用（条件付き）** | 索引 **860 tok ＝ 全文の 2.8%**（1 エントリ 78 tok）。台帳ロード **−71.0%〜−97.2%**（0〜3 件シナリオ）、固定文脈 **−33.4%〜−45.7%**。契約・board・`fp` への波及**すべてゼロ**。**条件**: 索引はファイル化せず**台帳からの投影**（stdout）に限る（`sync-free`）。§6 の T1〜T8 を実装より先に入れる |
| **3. 原文引用の置き場所** | **不採用** | 削減 −30.6% は案 2 と同等以下。一方で `fp` の更新検知が永久に効かなくなる（ingest-challenges が明文で禁じている形）・board の説明欄が退行（`CardDetailModal.tsx:310`）・アーカイブの恒久記録 **58,186 tok（65.2%）** を喪失。**案 2 が同じ削減を破壊なしに得る** |
| **4. 母数の削減** | **継続（採用済み）** | 剪定コミット `6dc6344` 単体で **42,207 → 28,098 tok（−33.4%）**。ただし **1 時間 43 分後**には +3,144 tok 戻っており、5 エントリ増で効果が相殺される。案 2 の代替にはならず、**乗算的に併用**する |

**あわせて確定した実装方針**:

- **D-1（索引の置き場所）**: 索引は **`scripts/` に投影スクリプトを 1 本追加**する形で実装し、
  **SKILL.md には `awk` ワンライナーを書かない**。散文へ落とすと SKILL.md が数百 tok 増え、
  かつ #97 で棚卸し中の分量課題と逆行する。スクリプトなら正常系の出力は索引そのものだけで、
  規定の文脈コストはほぼゼロになる（[run-cycle-context-budget.md §1.3](./run-cycle-context-budget.md)）。
- **D-2（内容判断を要するモードの扱い）**: `gdd-dogfood-first` / `release-freeze` が active の周は、
  **分類済エントリの全文を開くのを既定とする（fail-closed）**。件数上限は設けない。
  `priority-policy.md` のモード定義側に「索引で決まるか」の宣言欄は**足さない**——
  モード追加時の記入漏れが fail-open になるうえ、自走中に方針ファイルを編集する必要が生じるため
  （run-cycle 手順2 は自律実行中の `priority-policy.md` 書き換えを禁じている）。
  この周の削減率は最悪ケース（−16.2%）まで落ちるが、**判断材料が欠けるより安全側**である。
- **テストの順序**: §6 の T1〜T8 を**実装より先に**入れる。

## 8. 論点（D-1・D-2 は §7 で決定済み／D-3・D-4 は未決）

- **D-3（決定済み・実装で解消）**: 投影は**読み取り専用**で台帳にもワークスペースにも書かない
  ため、`--dry-run` による分岐を持たせる必要が無い（`--dry-run` は「変更・委譲・コミットを
  行わない」の意であり、読み取りは対象外）。順序についても、投影の呼び出しはロック取得と
  トランザクション回収の**後ろ**に置いた——回収は「台帳を書く前の fail-closed 検査」であり、
  読み込み方を変えても前後関係は動かない。読み取り専用であることは T6 が
  「書き込めないディレクトリでも投影できる」「実行してもファイルが増えない」で固定している。
- **D-4（未決・限界の明示）**: 本ドキュメントの tok はすべて `o200k_base` による代理指標であり、
  **Claude 上での測定ではない**（[run-cycle-context-budget.md §1.1] と同じ限界）。
  比率・順序の結論はバイト数からも同じ向きに出る（台帳の B/tok は 3.26 で
  比較対象 6 ファイルの 3.26〜3.47 に収まる）が、絶対値は別トークナイザで変わりうる。
- **D-5（未検証）**: §3.2 の「その周に開くエントリ数 1〜3 件」は設計上の想定であり、
  実測で確かめていない。journal から取れたのは「触った課題 中央値 5 件・範囲 2〜13 件」までで、
  そのうち索引で足りる件（ステータスのみ前進）と全文が要る件の内訳は分離できていない。
  §5-3 の検証で確定させる。
- **D-6（決定済み）**: 1-h（差し戻しの検出）は、**基準 SHA を持たず、承認待ち
  （`計画承認待ち` / `完了確認待ち`）のエントリを毎周全文で開く**ことで満たす（fail-closed）。
  `contracts/ledger-read-scope.tsv` の当該 2 行が `full` なのはこの決定による。
  - **`runs.jsonl` の `cycle_end` に `commit_sha` を足す案は採らなかった**。`contracts/schemas/runs.schema.json`
    は各イベントに `additionalProperties: false` を置いており、フィールド追加はスキーマ変更になる。
    このスキーマは board が vendoring する契約（`contracts/README.md` の 3 点セット）であり、
    単一リポジトリで閉じない。**本課題の範囲を越える**ため見送った。
  - **コミットメッセージの慣習から `git log --grep` で拾う案も採らなかった**。`cycle-commit.sh` の
    既定 subject は `chore(cycle): <cycle名>` だが `--message` で上書きでき（実運用の
    ワークスペースでも上書きされている）、機械可読な契約になっていない。
  - **代償は実測で 10,434 tok**（承認待ち 4 件・§5 の実測結果）。承認待ちは「人間の応答待ちで
    止まっているエントリ」であり構造上少数だが、滞留するとそのまま費用になる。
    範囲限定の差分で置き換えれば回収できるため、**スキーマ変更を伴う改善余地として残す**。
