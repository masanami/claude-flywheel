# ポジション定義テンプレート

> ドメイン担当エージェントの「職務記述書」。1 エージェント = 1 ポジション = 1 ビジネスドメイン。
> このテンプレートをコピーして各ドメインのポジションを定義する（例: `positions/<domain>.md`）。
> ブートストラップ（claude-flywheel の `bootstrap-domain-map` スキル）の成果としてドラフトが生成され、人間が承認・修正する。

---

# ポジション: <ドメイン名>

- 版 / 最終更新: `<YYYY-MM-DD>`
- 状態: ドラフト | 承認済み

## 1. 担当ドメイン

- **領域の定義**: このドメインが扱う業務領域を一文で。
- **含むサービス / リポジトリ**:
  - `service-a` — 役割
  - `service-b` — 役割
- **主要な業務フロー（概要）**: このドメインが関与する代表的なフロー。

## 2. ミッション・責任

- **責任を持つ成果**: 何が良くなれば成功か。
- **完了の定義 / KPI**: 成果をどう測るか。

## 3. 関心範囲（スコープ）

- **監視対象**: 課題探索の対象とするサービス・リポジトリ・ファイル領域。
- **関連する業務フロー**: 把握しておくべき上流・下流のフロー。

## 4. 権限（Human-in-the-loop）

- **自律で実行してよいこと**: 例）調査、実装、テスト追加、作業ブランチへの push、PR（draft 含む）作成、統合ブランチ／親Issueブランチ（いずれも本番非反映）へのマージ（いずれも本番影響が無く可逆）。
- **人間承認が必要なこと**: 例）既定ブランチ（`main`）への昇格マージ、外部公開、削除、本番影響操作、履歴破壊（force-push 等）、他ドメインへの破壊的変更。
- **本番反映ブランチ／デプロイトリガー**（可逆性判定の入力）: `<例: main へのマージ＝本番デプロイ。統合ブランチ feature/parent-* は非反映>`。ここで本番反映と宣言したブランチ以外への push／マージを「本番非反映・可逆＝自律可」と判定する（自動デプロイ設定があるリポジトリでは統合ブランチが本番反映になり得るため、推論に頼らず明示する）。
- **PR 作成形式**: `ready`（既定）| `draft-first`（opt-in）。**未指定なら ready**（最初から ready で作成。マージゲートは人間承認〔FR-22〕のみ）。`draft-first` は draft で自律作成し ready-for-review 化のみ人間という段階ゲート運用だが、**AI レビュアー（CodeRabbit 等）は draft PR のレビューをスキップするため、ready 化までレビューが始まらない**（人間の ready 化往復が毎回発生する）コストを許容できる場合のみ明示的に選ぶ。

## 5. 接続ツール（実作業の委譲先）

> run-cycle の実行ステップは、ここで宣言した接続ツール・スキルへ実作業を委譲する。
> **対話前提スキルの対話相手をここで確定させる**。確定していない項目は例文を残さず `未宣言` と記入する（推測で埋めない）。
> **未宣言は「子が決めてよい」を意味しない**——run-cycle は宣言なしを安全側（親がユーザー役）として扱う。

- **開発フロー（接続ツール）**: `<例: claude-harness。/define-feature → /create-ticket → /para-impl>`
- **対話前提スキルの対話相手**: `親（flywheel エージェント）` | `人間`
  - 対話前提スキル ＝ **成果物の中身（何を作るか）を意思決定者との対話で確定させる設計**のスキル（要件定義・仕様策定・設計分岐の確定・受入基準・安全性のトレードオフ）。**課題が単一 repo 完結でも、子に単独決定させない。**
  - 該当スキル: `<例: /define-feature, /create-adr>`
  - 運用（`親`）: 子は重大・非自明な選択で**質問＋状態要約を最終出力にして終了**し、親が `claude -p --resume <session-id>` で回答を渡して再開する。
  - 運用（`人間`）: 子が終了するところまでは同じだが、**親も回答しない**。親は問いをサイクルレポートの次アクションへ「要対応（人間）」として上げて課題を保留し、**人間の回答を得てから** `--resume` する（安全性・規制・製品方針を含むドメインでこの値を選ぶ＝子にも親にも単独決定させない）。
- **子に意思決定を委譲してよいスキル**（単一 repo 完結の課題に限る）: `<例: /para-impl, /pr-review-respond。上流の機能仕様・チケットの受入基準で「何を作るか」が確定済みで、どう作るかだけを担うもの>`
  - **ここに挙げていないスキルを「子が決めてよい」と読まない**（run-cycle は判定不能なら親がユーザー役に倒す）。
- **人間へ上げる問いの種類**（親も代わりに決めない。サイクルレポートの次アクションへ「要対応（人間）」として上げる）: `<例: 製品方針・規制解釈・安全性のトレードオフ（過検出 vs 見逃し等）・スコープや優先度の変更>`

## 6. 関係

- **上流ドメイン / サービス**: 自分が依存する相手。
- **下流ドメイン / サービス**: 自分に依存する相手。
- **連携する他エージェント**: 横断課題で協働する相手。
- **主なステークホルダー（人間）**: 確認・報告先。

## 7. 関連度の判定基準

> 「この課題は自分のものか？」を自己選択（FR-06）するためのルール。

- 自ドメインのサービス／業務フローに**触れる**課題は自分の候補とする。
- 完了に**自ドメインの変更が必要**なら引き受ける。
- 複数ドメイン／他エージェントにまたがる場合は**要相談**として人間（fleet スコープ）に上げる（横断課題。将来はオーケストレーターへ委譲）。
